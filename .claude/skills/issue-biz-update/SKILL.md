`issue-biz-create` で作成したビジネス共有用Issueを、ビジネスサイドへの共有可否のルールを保ったまま更新するワークフローです。

---

# Issue Update Workflow（ビジネス共有版）

## このskillの位置づけ

- 対象は **`issue-biz-create` で作成したIssue**（共有部分 + 折りたたみコードマッピングメモ の構成を持つもの）。
- **共有部分（概要 / ユースケース / 詳細仕様 / 受け入れ条件）はコード参照なしを維持する。**
- 折りたたみメモ（`🔧 開発者用：コードマッピングメモ`）も、共有部分の変更に連動して更新する。
- 通常の `issue-update` との違い: `issue-update` は本文に「実装設計」「技術考慮」「テスト担保（T-N/ツール名）」を**直接書き込む**ため、ビジネス共有用Issueの本文に使うと共有禁止のコード情報が混入する。本skillは混入を防ぐ。

> **実装着手フェーズへの移行**: ビジネス合意が取れて実装に進む場合は、本skillではなく `issue-update` を使い、折りたたみメモを入力として「実装設計／技術的な考慮事項／テスト担保方針」を展開する。その際は共有用Issueとは別運用（または本文を開発者向けに昇格）とすることをユーザーに確認する。

## ARGUMENTS
- `ISSUE_NUMBER [変更内容]`: 対象Issue番号。続けて変更内容を書いた場合は、その指定変更のみを反映する（手動更新モード）。変更内容がなければ、Issue全体を再分析して洗練する（洗練モード）。

## IMPORTANT
- **Planモードに入ることを禁止する。**
- **共有部分にコード上の固有名詞を入れない**（ファイルパス/クラス名/関数・メソッド名/変数名/テーブル・カラム名/APIエンドポイント/コンポーネント名/テストツール名/サブリポジトリ名等）。
- 用語ルール（対象画面 / 対象ラベル / 対象項目 / 対象ロジック）と受け入れ条件のQA可能性は `issue-biz-create/SKILL.md` に従う。

## 手順 (Steps)

### 1. 現状の把握
```
$ gh issue view ISSUE_NUMBER --repo akichim21/cancel --json title,body,labels,comments
```
本文を「共有部分」と「折りたたみメモ」に分けて把握する。`ISSUE_NUMBER` に続けて変更内容が指定されていれば、その変更がどのセクションに影響するか（追加/修正/削除）を特定する。

### 2. コンテキストの補足収集（必要時のみ）
- 変更内容に関連する仕様が `docs/product/` にあれば確認し、画面/ラベルの正式名称を再確認する。
- コードへの対応づけが新たに必要な場合のみ、関連箇所を軽く調査して折りたたみメモの対応表を補強する（共有部分には持ち込まない）。
- 受け入れ条件を変える場合は、人間の画面操作でQA可能な手順になるよう設計する。

### 3. 差分の分析 (Diff Analysis)
* **変更箇所**: 概要 / ユースケース / 詳細仕様 / 受け入れ条件 のどこを変えるか。
* **連動チェック**:
  - 詳細仕様（REQ-N）を追加/変更/削除 → 対応する受け入れ条件（AC）と折りたたみメモの「REQ→想定変更箇所」を連動更新する。
  - 受け入れ条件を追加/変更/削除 → 折りたたみメモの「AC→想定テスト」を連動更新する。QA手順・期待結果も見直す。
  - 対象画面/ラベル/項目の名称が変わった → メモの「用語↔コード対応表」を更新する。
* **コード混入チェック**: 変更によって共有部分にコード名・ツール名・サブリポジトリ名が混入しないことを確認する。混入させる必要がある情報は折りたたみメモへ振り分ける。

### 4. 更新案の作成 (Drafting)
- 既存の本文構成（共有部分 + 折りたたみメモ）を維持する。変更に関係ないセクションは書き換えない（最小差分）。
- 手動更新モードでは指定変更のみ反映する。洗練モードでは曖昧さの解消・網羅性向上を行うが、共有/非共有の分離は厳守する。
- 本文末尾の `## 元の文章 (Original Text)` 運用: 手動更新モードで変更内容の指示文を追記する場合は折りたたみメモより前、共有部分の末尾の `元の文章` セクションに追記する（無ければ作成）。`issue-biz-create` 由来の構造化済みIssueでは省略してよい。

### 5. 実行 (Execution)
1. 変更前後の差分をユーザーに提示する（**変更セクション名 / 変更前 / 変更後**）。共有部分と折りたたみメモの両方の差分を示す。
2. 承認後、本文全文（共有部分 + 折りたたみメモ）で更新する。
   ```
   $ gh issue edit ISSUE_NUMBER --repo akichim21/cancel --body "$(cat <<'BODY_EOF'
   更新後のMarkdownテキスト全文
   BODY_EOF
   )"
   ```

## 思考プロセスへの指示 (Guidelines)
* **最小差分の原則**: 指定された変更のみ反映する。「ついで」の改変をしない。
* **共有部分とコードの完全分離の維持**: 更新時も共有部分にコード固有名詞を混入させない。
* **構造の保持**: 共有部分 + 折りたたみメモ の構成・見出しを維持する。
* **整合性の確認**: 詳細仕様⇄受け入れ条件⇄折りたたみメモ（対応表/REQ→変更箇所/AC→テスト）の連動を保つ。
* **QAできるAC**: 受け入れ条件は人間が画面操作で確認できる手順・期待結果で書く。
* **ドキュメント優先**: `docs/` に仕様がある場合は優先し、矛盾があれば警告する。
* **Issue 登録先は `akichim21/cancel` 固定**: Issue は親リポジトリ `akichim21/cancel` に集約する。サブリポジトリ（`GO-TODAY-SHAiRE-SALON/cancel-billing-service-*`）の origin が検出されても、そちらは参照・更新しない。`gh issue` 系は `--repo akichim21/cancel` を明示すること。
