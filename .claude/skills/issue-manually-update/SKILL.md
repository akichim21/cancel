# Issue Manual Update Workflow

指定されたGitHub Issueに対して、ユーザーが指定した変更内容を反映してIssueを更新するワークフローです。
全体を再分析するのではなく、指定された変更点のみを既存Issueに適用します。

## ARGUMENTS
- `ISSUE_NUMBER 変更内容`: スペースまたは改行区切りで、先頭がIssue番号、残りが変更内容の説明

例: `123 受け入れ条件にエラーハンドリングのテストケースを追加し、変更内容からマイグレーション手順を削除する`
例: `123
受け入れ条件にエラーハンドリングのテストケースを追加し、変更内容からマイグレーション手順を削除する`

## 手順 (Steps)

### 1. Issueの取得と変更内容の把握

```
$ gh issue view ISSUE_NUMBER --repo akichim21/cancel
```

取得したIssue本文と、ARGUMENTSで指定された変更内容を照合し、以下を判断する。

- 変更内容がIssueのどのセクションに影響するか
- 追加・修正・削除のいずれか
- 既存の記述との矛盾や重複がないか

### 2. コンテキストの補足収集 (Context Gathering)

変更内容に応じて、**必要な場合のみ** 以下を実施する。（軽微な文言修正なら省略可）

1. **ドキュメント検索**: 変更内容に関連する仕様が `docs/*.md` にあれば確認する。
2. **コード検索**: 変更内容が実装に関わる場合、関連ファイルを検索して現状を確認する。
3. **受け入れ条件**を変更すべき時は、.claude/skills/qa-patterns/のベストプラクティスを確認し、今回のissueでテスト追加、変更、削除すべきパターンを洗い出す

### 3. 差分の分析 (Diff Analysis)

現在のIssue本文と変更内容を比較し、以下を明確にする。

* **変更箇所**: どのセクション（概要 / 前提条件 / ユースケース / 詳細仕様 / 実装設計 / 技術的考慮事項 / 受け入れ条件 / 未解決の質問）のどの部分を変えるか
* **変更の種類**: 追記 / 修正 / 削除
* **影響範囲**: あるセクションの変更が他のセクション（特に詳細仕様・受け入れ条件）にも波及しないか確認する
* **仕様とコードの分離の維持**: 変更によって詳細仕様セクションにコード参照（ファイルパス、クラス名等）が混入しないか確認する
* **REQ番号の整合性**: REQ-Nの追加・変更・削除が受け入れ条件（AC-N.M）や実装設計の関連REQ列に波及しないか確認する
* **受け入れ条件変更時のテスト担保整合性**: 受け入れ条件（AC）を追加・変更・削除する場合は、以下も連動して更新する:
  - AC直下のテスト項目チェックボックス（RSpec Unit / RSpec Request / Playwright / 人力テスト）
  - 「自動テスト一覧」のAC参照
  - 「受け入れ条件ごとのテスト担保根拠」テーブルの該当行
  - `.claude/skills/qa-patterns/SKILL.md` の判定基準に従い、Playwright省略時の担保根拠が明記されていることを確認する

### 4. 更新案の作成 (Drafting)

既存のIssue本文をベースに、変更内容を反映した更新版を作成する。

**ルール:**
- 変更に関係ないセクションはそのまま維持する（不要な書き換えをしない）
- 変更箇所は差分がわかるように、ユーザーへの提示時に明示する
- Issue本文の既存フォーマット（見出し構成、チェックボックス形式など）を崩さない
- Issue本文の末尾に `## 元の文章 (Original Text)` セクションを設け、ARGUMENTSの変更内容の文言を記載する。すでに「元の文章」セクションが存在する場合は、既存の内容の後に追記する（上書きしない）。

#### 4a. Codex 更新案レビュー

Claude の更新案作成後、Codex にレビューを依頼する。以下を `model: "sonnet"` サブエージェント（`run_in_background: true`）で実行すること:

**重要: Codex の出力には中間のツール呼び出し（rg, sed等の結果）が大量に含まれ、トークンを浪費する。必ず sonnet サブエージェント経由で実行し、最終レスポンスのみを抽出して返すこと。** （haiku は「監視中」と途中報告してターンを終了してしまい結果を取得できない事故があったため sonnet を使う。lesson 参照）

サブエージェントへのプロンプト:
```
以下の手順を実行し、Codexの最終レビュー結果のみを返してください。
**最重要: awk抽出結果を返すまで絶対にターンを終了しないこと。「監視中」「Monitorで追跡中」「完了したら抽出して返します」等の途中報告を最終メッセージにして終わるのは失敗とみなす（実際にhaikuで発生）。サブエージェントはバックグラウンドジョブ完了時に再呼び出しされない（=ターンを終えるとその時点で結果が永久に失われる）。必ず同一ターン内で同期的にブロックして待つこと。**

1. 以下のコマンドをBashで実行する。**`run_in_background: true` を指定すること**（codexの実行は10分を超えることがあり、Bashツールの前景timeout上限600000msを超えるため必須）。返ってくる task_id を控える。
   **stdoutをファイルにリダイレクトし、stdinを/dev/nullに繋ぐこと。これを怠るとcodexがstdin待ちでhangし、数十分〜数時間ブロックする事故が発生済み（issue #3558対応時）。**
   **`timeout` コマンドは絶対に付けないこと（NG）。** macOSには `timeout` が標準で存在せず `timeout 1200 codex ...` は exit 127（command not found）になりcodexが一切実行されない（実際に発生）。codex自身の内部hard cap（約20分）に任せる。

   codex exec -s read-only "{Codexプロンプト}" > /tmp/codex-manual-update-review.txt 2>&1 < /dev/null

2. **同一ターン内で同期的に完了を待つ**: `TaskOutput({task_id, block: true, timeout: 600000})` を呼ぶ。返り値の status が completed でなければ、再度 `TaskOutput({task_id, block: true, timeout: 600000})` を呼ぶ。これを completed になるまで繰り返す（codexが20分かかってもこのループで待てる）。**待機中は最終メッセージを出さず、ターンを終了しないこと。** 途中経過のBashOutputを見て独自に打ち切らない。

3. 完了後、出力ファイルからCodexの最終レスポンスのみを抽出する:

   LAST_LINE=$(grep -n "^codex" /tmp/codex-manual-update-review.txt | tail -1 | cut -d: -f1)
   awk "NR>=${LAST_LINE}" /tmp/codex-manual-update-review.txt

4. awkの出力のみを返す。要約や加工は不要。出力ファイル自体をReadで読まないこと。
5. 異常終了の判定は task が completed になった後にのみ行う。出力に `codex` から始まる最終応答ブロックが無く、かつ exit code が 127 の場合は「Codex unavailable（codexコマンド未検出。PATHを確認）」と返す。それ以外で最終応答が無い場合は出力末尾のエラー行をそのまま返す。無理に再試行しない。
```

Codexプロンプト:
```
⚠️ READ-ONLY: ファイルの作成・編集・削除は絶対に行わないこと。レビューコメントをテキストで報告するのみ。

以下のGitHub Issue更新案をレビューしてください。まずAGENTS.mdを読んでリポジトリ構造を把握すること。また `.claude/skills/qa-patterns/` と `.claude/skills/issue/` 配下のファイルが存在する場合は読み、レビュー基準として活用すること。

【既存Issue本文】
{既存Issue本文の全文を展開}

【変更内容】
{ARGUMENTSの変更内容を展開}

【Issue更新案】
{Step 4で作成した更新案の全文を展開}

【レビュー観点】
- 変更内容が正しく反映されているか
- 変更に関係ないセクションが意図せず変わっていないか
- 詳細仕様・受け入れ条件・実装設計の整合性
- フォーマットの一貫性
```

**⚠️ 結果待機の手順（2a と同じ手順に従うこと）:**
1. `TaskOutput` で完了状態を確認する
2. 未完了なら状況をユーザーに報告し待機する
3. 15分以上なら途中出力を確認しユーザーに判断を仰ぐ
4. 妥当な指摘は更新案に反映し、出典タグを付ける（例: `[~Codex@4a] フォーマット調整`）。ユーザーへの提示時に「**Codex活用レポート**」セクションを設け、以下を表示する:
   - **反映箇所**: Codex由来の変更一覧（各項目にステップ番号を明記）
   - **不要だったステップ**: Codexの情報がClaude自身の分析に対して新規情報を提供しなかったステップを明記する（例: 「2a: Codex — Claude の調査と重複する情報のみ」）

### 5. 実行 (Execution)

1. 変更前後の差分をユーザーに提示し、レビューを求める。提示形式:
   - **変更セクション名**
   - **変更前**: 該当部分の抜粋
   - **変更後**: 更新後の内容
2. ユーザーの承認が得られたら、以下のコマンドでIssueを更新する。
   ```
   $ gh issue edit ISSUE_NUMBER --repo akichim21/cancel --body "更新後のMarkdownテキスト全文"
   ```

## 思考プロセスへの指示 (Guidelines)

* **最小差分の原則**: 指定された変更内容のみを反映せよ。「ついでに」他の箇所を改善しない。
* **構造の保持**: 既存のIssue本文のセクション構成・フォーマットを維持せよ。セクションの順序変更や見出しレベルの変更はしない。
* **仕様とコードの分離の維持**: 変更を反映する際、詳細仕様セクションにファイルパス・クラス名等のコード参照が混入しないようにせよ。コードレベルの情報は実装設計セクションに記載する。
* **整合性の確認**: 変更によって他のセクションとの矛盾が生じる場合は、ユーザーに指摘した上で修正案を提示せよ。特に詳細仕様の変更は受け入れ条件や実装設計にも影響しうるため、関連セクションの整合性を確認すること。
* **ドキュメント優先**: `docs/` に仕様がある場合はコードより優先し、変更内容がドキュメントと矛盾する場合は警告せよ。
* **過剰品質の防止**: 文言の微修正に対して大掛かりな再分析を行わないこと。変更の規模に応じた作業量にせよ。
