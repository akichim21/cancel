ビジネスサイド（非エンジニアの企画/運用/サロン担当/QA）と共有することを前提に、GitHub Issueを新規作成するワークフローです。

---

# Issue Creation Workflow（ビジネス共有版）

## このskillの位置づけ（issue-create との違い）

| | issue-create | issue-biz-create（本skill） |
|---|---|---|
| 想定読者 | エンジニア | **ビジネスサイド + エンジニア** |
| 本文に含めるもの | 概要〜実装設計・技術考慮・テスト担保（コード参照あり） | **概要・ユースケース・詳細仕様・受け入れ条件のみ**（コード参照なし） |
| コードへの言及 | 実装設計セクションに集約してOK | **本文の共有部分は一切禁止**。折りたたみメモにのみ記載 |
| 受け入れ条件 | T-N / Jest / Playwright 等のテスト種別を併記 | **ビジネス担当者が画面操作でQAできる手順**として記述（ツール名禁止） |
| 後工程 | そのまま実装着手 | `issue-update` / `issue-biz-update` でメモを実装設計へ展開してから着手 |

**共有対象（ビジネスサイドが読むのはここまで）**: 概要 / ユースケース / 詳細仕様 / 受け入れ条件
**非共有（折りたたみ内・開発者専用）**: コードマッピングメモ

## ARGUMENTS
- `SOURCE_DOCUMENT`: Issueの元となる文書（テキスト、要件メモ、仕様書のパス等）

## IMPORTANT
- **Planモードに入ることを禁止する。** 直接実行すること。
- **共有部分（概要・ユースケース・詳細仕様・受け入れ条件）には、コード上の固有名詞を一切書かない。** 禁止例: ファイルパス、クラス名、関数名・メソッド名、変数名、テーブル/カラム名、APIエンドポイント、コンポーネント名、テストツール名（Playwright/Jest/Vitest 等）、ライブラリ名、サブリポジトリ名（cancel-billing-service-* 等）。
- `SOURCE_DOCUMENT`に具体的な手順や仕様が記載されてる場合は意味を変更したり、具体性を減らさないこと。
- 不整合やより良い仕様への変更余地がある場合は、質問・提案を行って確認をとること。

## 用語ルール（共有部分の書き方）

画面に紐づく要件は、コード名ではなく**人間が画面を見て分かる日本語**で対象を特定する。可能な限り画面のタイトル・名称を使い、「どこを変えるのか」が一目で分かるようにする。

| 用語 | 意味 | 例 |
|------|------|----|
| **対象画面** | どの画面か。画面のタイトル/名称で表す | 「請求一覧画面」「サロンポータル＞キャンセル申請」 |
| **対象ラベル** | 画面上に表示される文言・ボタン名・見出し | 「申請するボタン」「『確定』ボタン」「ステータス表示」 |
| **対象項目** | 入力欄・表示項目・カラムなど | 「メールアドレス入力欄」「請求金額の表示」 |
| **対象ロジック** | 画面に紐づかない処理・自動処理。**バッチは「◯◯バッチ（毎日◯時に自動実行される処理）」のように説明する** | 「日次請求集計バッチ」「リマインドメール送信処理」 |

- 対象アプリは日本語名で明記する: **サロンポータル / 管理画面 / LP・申請フォーム / バックエンド処理（API・バッチ）**。
- 「適切に」「必要に応じて」等の曖昧表現は禁止。条件と結果を具体的に書く。

## 手順 (Steps)

### 0. 進捗確認と再開

**進捗ファイル**: `.claude/tmp/${REPO_NAME}-issue-biz-create-*.json`

`.claude/tmp/` 配下に該当ファイルがあれば最新を読み込み未完了ステップから再開、なければ `.claude/tmp/${REPO_NAME}-issue-biz-create-$(date +%Y%m%d%H%M%S).json` を新規作成する。各ステップ完了時に更新する。

### 1. 入力文書の把握

`SOURCE_DOCUMENT` を読み込み、以下を把握する。
- 何をしたいのか（目的・背景）
- 対象となる画面・機能・処理はどこか
- 対象アプリ（サロンポータル/管理画面/LP/バックエンド）はどれか
- 明示されている制約や条件

### 2. コンテキスト収集（共有部分の正確さ + メモ作成のため）

ビジネス共有部分を正確に書き、かつ後工程用のコードマッピングメモを作るために、軽く調査する（コード深掘りは不要、docs中心でよい）。

1. **ドキュメント検索**: `docs/product/` を中心に関連仕様・画面名・正式名称を確認する。画面/ラベルの正式名称はここで確定させる。
2. **画面・対象の特定**: 対象画面のタイトル/ラベル/項目の実際の表記を確認する（UIテキスト）。曖昧なら `codebase-explorer` エージェント（`.claude/agents/codebase-explorer.md`）を生成して、対象画面・コンポーネント・処理・APIの実体を調べさせ、**日本語表現↔コードの対応**を集める。
3. **Lesson確認**: `.claude/skills/issue/lesson.md` を読み、過去の指摘パターンを回避する。

調査で得た「日本語表現 → コード上の場所」の対応は、Step 5 のメモ作成のために控えておく。**ただし共有部分には絶対に持ち込まない。**

### 3. 分析と具体化 (Analysis)

* **変更対象の特定**: 新規（新画面/新処理）か既存改修かを判定。既存改修なら対象画面/対象ロジックのどこを変えるか具体化する。
* **ユースケース分析**: 新規ユーザーフロー導入 → 詳細フロー記述。既存フロー修正 → 1行参照。バグ修正・軽微改修 → ユースケース省略可。
* **仕様の網羅性**: 画面/機能ごとに 表示仕様・条件分岐・バリデーション・エッジケース を洗い出す。
* **対象アプリの明記**: サロンポータル/管理画面/LP/バックエンド を明確化。
* **規模感 (Calibration)**: Low（文言修正・軽微）はシンプルに、High（新機能・複雑なロジック）は網羅的に。大きすぎる場合はサブissue分割を提案する。
* **要件番号付与**: 詳細仕様の各ブロックに REQ-N を付与する。
* **QA可能性**: 各受け入れ条件が「画面を操作して人間が真偽判定できる」粒度かを確認する。

### 4. ビジネス共有用Issue本文の作成 (Drafting)

以下を **Markdown形式・コード参照なし** で作成する。書き方は `.claude/skills/issue/writing-usecases.md` / `writing-spec.md` を参考にしつつ、**コード参照は全て省略し「用語ルール」の日本語表現に置き換える**こと。

```markdown
## 概要 (Overview)
何をするタスクで、なぜ必要か（背景・課題・狙い）をビジネス担当者向けに記述する。

## ユースケース (Use Cases)
（新規フロー導入時のみ詳細記述。UC-N形式。アクター・基本フロー（画面遷移）・代替フロー・事後条件）

## 詳細仕様 (Detailed Specification)

### REQ-1: [対象画面の名称] [対象アプリ]
[日本語散文]。対象画面・対象ラベル・対象項目・対象ロジックを使って、表示仕様／条件分岐／入力制約・エラー表示／操作時の挙動を具体的に記述する。コード名は書かない。

### REQ-2: [対象ロジックの名称（例: 日次請求集計バッチ）] [バックエンド処理]
[日本語散文]。バッチ等は「いつ・何をトリガに・何をする処理か」を平易に説明する。

## 受け入れ条件 (Acceptance Criteria)
（下記「受け入れ条件の書き方」に従う）
```

#### 受け入れ条件の書き方（ビジネスQA版）

- **ビジネス担当者が画面を操作して真偽判定できる手順**で書く。テストツール名（Playwright/Jest/Vitest等）・自動テスト種別・T-N は**書かない**（それらはメモ側に書く）。
- 各ACは「どの画面で・何を・どうすると・どうなるか」を含める。対象画面/対象ラベル/対象項目を明記する。
- 必要に応じて `QA手順` を番号付きで添え、最後に `期待結果` を書く。
- 対応する詳細仕様を `(REQ-N)` で参照する。

```markdown
## 受け入れ条件 (Acceptance Criteria)

- [ ] AC-1: 「キャンセル申請画面」で必須項目がすべて入力されているとき、「申請するボタン」が押せる状態で表示されること（REQ-1 / サロンポータル）
  - QA手順: 1. 必須項目をすべて入力 2.「申請するボタン」の状態を確認 → 期待結果: ボタンが活性（押下可能）で表示される
- [ ] AC-2: 必須項目に未入力があるとき、「申請するボタン」が押せない状態で表示され、未入力項目にエラー文言が表示されること（REQ-1 / サロンポータル）
- [ ] AC-3: 「申請するボタン」押下後、申請が受け付けられ「申請完了」画面に遷移すること（REQ-1 / サロンポータル）
  - QA手順: 1. 全項目入力し「申請するボタン」押下 → 期待結果:「申請完了」画面が表示され、管理画面の請求一覧に新規申請が表示される
- [ ] AC-4: 日次請求集計バッチが実行されると、前日確定分の請求が管理画面の「請求一覧画面」に集計表示されること（REQ-2 / バックエンド処理）
  - QA手順: バッチ実行 → 期待結果:「請求一覧画面」に前日確定分が反映される
```

### 5. 開発者用コードマッピングメモの作成（折りたたみ・非共有）

Step 2 で集めた「日本語表現↔コード」対応を、本文の**末尾に折りたたみ（`<details>`）**で付ける。これは後工程（`issue-update` / `issue-biz-update`）が**実装設計・技術考慮・テスト担保へ展開するための変換テーブル**である。

```markdown

---

<details>
<summary>🔧 開発者用：コードマッピングメモ（ビジネス共有対象外 / issue-update で実装設計へ展開する）</summary>

> このセクションはエンジニア専用。ビジネスサイドへの共有・QA対象外。
> 本文の日本語表現を実コードへ対応づける。`issue-update` 実行時にこの表を元に「実装設計」「技術的な考慮事項」「テスト担保方針」を生成する。

### 用語 ↔ コード対応表
| 本文の表現 | 種別 | 実体（サブリポジトリ / コード上の場所） | 補足 |
|-----------|------|----------------------|------|
| 「キャンセル申請画面」 | 画面 | cancel-billing-service / `src/.../ApplicationForm.tsx` | サロンポータル |
| 「申請するボタン」 | ラベル | `SubmitButton` コンポーネント | |
| 請求ステータス | 項目 | DB `billings.status`（draft/confirmed/...） | |
| 日次請求集計バッチ | ロジック(バッチ) | cancel-billing-service-api / Lambda `aggregateBillingsHandler`（cron 毎日09:00 JST） | |
| 申請API | API | cancel-billing-service-api / `POST /applications` ハンドラ `createApplicationHandler` | |

### REQ → 想定変更箇所
| REQ | 対象アプリ / サブリポジトリ | 想定変更ファイル/関数 | 補足 |
|-----|----------|---------------------|------|
| REQ-1 | サロンポータル / cancel-billing-service | `ApplicationForm.tsx` / `SubmitButton` | 必須バリデーションで活性制御 |
| REQ-2 | バックエンド / cancel-billing-service-api | Lambda `aggregateBillingsHandler` | |

### AC → 想定テスト（種別・ツール）
| AC | 想定自動テスト | ツール |
|----|--------------|--------|
| AC-1〜AC-3 | 申請フォーム入力〜送信フロー | Playwright（サロンポータル） |
| AC-4 | 集計ハンドラのロジック | Jest（API・unit + ハンドラ統合） |

### 実装上の懸念・補足
- （データ整合性・認可・マイグレーション・パフォーマンス・Lambda タイムアウト等の覚書）

</details>
```

> メモの粒度は規模に応じて調整する。Low規模なら対応表数行で十分。

### 6. レビュー（軽量）

草案完成後、最低限以下を自己点検する。必要なら `.claude/skills/issue/lesson.md` 準拠を確認する。

- [ ] 共有部分（概要〜受け入れ条件）に**コード名・テストツール名・サブリポジトリ名が一切混入していない**
- [ ] 各要件が対象画面/対象ラベル/対象項目/対象ロジックで特定されている
- [ ] 各ACがビジネス担当者の画面操作でQA可能（真偽判定可能）
- [ ] REQ ↔ AC が対応している
- [ ] 折りたたみメモが `<details>` 内に収まっている

規模が大きい場合のみ、`.claude/agents/docs-reviewer.md` を生成して docs整合性・lesson違反をレビューさせてよい。

### 7. 実行 (Execution)

> **Issue 登録先のルール**: Issue は **`akichim21` のリポジトリ（`akichim21/cancel`）に登録する**。サブリポジトリ（`GO-TODAY-SHAiRE-SALON/cancel-billing-service-*`）の origin が検出されても、そちらには登録しない。横断的な機能（api + admin など複数アプリにまたがるもの）も `akichim21/cancel` に集約する。`--repo akichim21/cancel` を明示すること。

1. 草案（共有部分 + 折りたたみメモ）とタイトル案をユーザーに提示し、レビューを求める。
2. 承認後、以下でIssueを作成する（本文末尾に折りたたみメモを含めた**全文**を渡す）。
   ```
   $ gh issue create --repo akichim21/cancel --title "提案タイトル" --body "$(cat <<'BODY_EOF'
   作成したMarkdownテキスト（共有部分 + 折りたたみメモ）
   BODY_EOF
   )"
   ```
3. ビジネス共有用ラベル（例: `Biz Review` 等、リポジトリに存在すれば）を付与する。`Ready to Develop` は**まだ付けない**（実装設計が未展開のため）。実装設計まで展開できたら付与する運用とする。

## 思考プロセスへの指示 (Guidelines)

* **共有部分とコードの完全分離**: 概要・ユースケース・詳細仕様・受け入れ条件にコード固有名詞を一切入れない。コード情報は折りたたみメモにのみ書く。
* **画面の場所を分かりやすく**: 可能な限り画面タイトル・メニュー名・ボタン名で「どこを変えるか」を示す。
* **QAできるAC**: 受け入れ条件は人間が画面操作で確認できる手順・期待結果で書く。
* **条件分岐の網羅**: 曖昧表現を禁止し、条件と結果を明記する。
* **過剰品質の防止**: タスク規模に応じて出力量を調整する。
* **元の意図の保持**: 入力文書の意図・文脈を損なわない。
* **後工程への橋渡し**: 折りたたみメモは `issue-update` / `issue-biz-update` が実装設計へ展開するための変換テーブルである。日本語表現とコードの対応が追えるように書く。
* **Issue 登録先は `akichim21/cancel` 固定**: サブリポジトリの origin が検出されても、Issue は `akichim21/cancel` に登録する（`--repo akichim21/cancel` を明示）。横断的な機能もここに集約する。
