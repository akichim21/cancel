# Issue Lesson - レビュー指摘パターン集

> このファイルはレビュー指摘や実装中に学んだパターンを記録します。
> Issue の作成・更新ワークフロー時に参照し、同じミスの再発を防ぎます。

## パターン一覧

### E2Eテスト（Playwright）はアクション実行＋結果検証まで含める
- **問題**: PlaywrightのE2Eテストが画面表示の確認（フォーム描画、ボタン状態）だけで終わり、実際のアクション（作成・保存・実行等）を実行して結果を検証していなかった
- **正しい対応**: E2Eテストはユーザー操作の全フローを実行し、結果を後続画面で検証すること。表示確認だけのテストは unit テストに任せる
- **例**:
  - NG: 申請フォームで入力項目の表示だけ確認 → OK: 実際に申請を送信し、完了画面/一覧に反映されたことを検証
  - NG: 管理画面の申請一覧表示だけ確認 → OK: 審査ステータスを変更し、ステータス変更が一覧/詳細に反映されたことを検証
  - NG: サロンポータルのキャンセル請求一覧表示だけ確認 → OK: 請求操作を実行し、ステータス変更を一覧/詳細で検証

### 通知フロー仕様は実装コードと照合してから確定する
- **問題**: Issue仕様に「サロンと顧客の両方にメール／SMS」と記載したが、実装では片方のみだった。仕様と実装の齟齬があるままIssueを作成すると、実装者が誤った方向で作業する
- **正しい対応**: 通知・メール・SMS等のコミュニケーション仕様を書く際は、`cancel-billing-service-api` の該当アクションのサービス層を読み、SES（メール）/ Twilio（SMS）の送信先・送信条件を確認する
- **チェック手順**:
  1. 該当アクションのハンドラ/サービス（`cancel-billing-service-api/src/`）を読む
  2. メール（SES）送信先と SMS（Twilio）送信先、送信トリガー条件を確認
  3. Issue仕様の通知送信先・タイミングが実装と一致しているか照合
  4. 不一致があれば実装に合わせるか、意図的な変更であることを明記

### 既存ドキュメントとの整合性を確認する
- **問題**: Issue仕様がdocs/product/配下の既存ドキュメント（例: cancellation.md）の記述と矛盾していた。具体例: 特定の申請ステータスでは「いつでも操作可能」と既存docsに記載があるのに、新仕様で当該ステータスにも制限を適用する設計になっていた
- **正しい対応**: Issue草案作成後にdocs-reviewerエージェントで既存ドキュメントとの整合性を検証する。矛盾がある場合は、意図的な仕様変更であることを確認事項として明記し、ユーザーに確認する。承認後はdocs更新もスコープに含める

### Issue仕様で参照する関数名は実装コード上の正確な名前を使用する
- **問題**: Issue草案で参照実装の関数名を記憶で書いたところ、実際のロジックは別関数だった。誤った関数参照により実装者が間違ったアルゴリズムを選択するリスクがあった
- **正しい対応**: 仕様に関数名・メソッド名を記載する際は、必ずGrepで実装を確認し、正確な関数名・ファイル名・行番号を記載する。類似名称の関数が複数ある場合は、それぞれの用途の違いを明記する
- **チェック手順**:
  1. 仕様に記載する関数名を `Grep` で検索
  2. 関数の実装を読み、仕様の目的と合致しているか確認
  3. 類似名称の関数が存在する場合は用途の違いを明記する

### 新規作成か既存改修かが曖昧なまま仕様を書いた
- **問題**: 仕様に「〇〇機能を追加する」とだけ書き、新規ページ作成なのか既存ページへの追加なのかを明示しなかった結果、実装者が誤った場所に実装して手戻りが発生した
- **正しい対応**: 仕様には必ず「新規作成」か「既存の○○ページ/バッチの○○部分を改修」かを明記する。曖昧な場合はユーザーに確認する

### AC間の依存関係（テストインフラ前提条件）を明示化する
- **問題**: AC-1.3（一覧テーブルの表示検証）がREQ-2（seedデータに値追加）に暗黙的に依存していたが、依存関係が明記されていなかった。実装者がREQ-1だけ着手しても、seedデータがないためテストが通らない
- **正しい対応**: ACがテストインフラ（seedデータ、環境設定など）に依存する場合、ACに「前提: REQ-Nが完了していること」と明記する。特にPlaywrightテストのseedデータ依存は見落としやすい
- **チェック手順**:
  1. 各ACが検証時にどのデータを必要とするか確認
  2. そのデータが他のREQで作成されるものであれば依存関係を明記
  3. 共有テストインフラ（seed/フィクスチャ）の変更は影響範囲を明記（Playwright/Jest 両方に影響）

### リポジトリまたぎの Issue は「完了条件」と PR 分割を明示する
- **問題**: Issue #53（LP リファクタ）の草案で、コード変更（サブリポジトリ `cancel-billing-service-*`）とドキュメント/skill 変更（親リポジトリ `cancel`）を 1 つのファイル変更一覧に並べたが、**別 Git リポジトリなので単一 PR では全 AC を満たせない**ことが未定義だった。実装者が「どこまでやれば完了か」を判断できない
- **正しい対応**: 変更が親リポジトリとサブリポジトリにまたがる場合、技術的考慮事項に以下を明記する
  1. どの REQ がどのリポジトリの PR に属するか
  2. 両方のマージをもって Issue 完了とすること
  3. 実装順序（通常はコード PR → docs/skill 反映。設計方針は実装で確定した内容を反映するため）
- **チェック手順**: ファイル変更一覧の「リポジトリ」列に 2 種類以上の値が出たら、この節を必ず書く

### 「見た目不変」リファクタ Issue は既存コンポーネントの暗黙仕様を先に洗い出す
- **問題**: Issue #53 の草案レビューで、LP の `Label` / `Badge` が **`className` を受け取っても黙って無視する**実装であること（呼び出し側は無視される前提でクラスを渡している）が、3 レビュアー全員から指摘された。抽出時に「ついでに props spread へ統一」すると無視されていたクラスが突然適用され、見た目不変の前提が崩れる。`Button` の「クラス指定時は色クラスを全置換」も同種の暗黙仕様
- **正しい対応**: 見た目・挙動不変を条件とするリファクタ Issue では、移動対象コンポーネントの **prop の受け取り方**（spread の有無 / 特定 prop の黙殺 / クラスのマージか全置換か）を実装で確認し、仕様へ「現状の API を維持する」または「どう変えるか」を明記する。黙殺仕様をそのまま新コンポーネントへ持ち込むのは避け、呼び出し側の死んだ指定を削除する形で解消する
- **チェック手順**: 抽出対象の各コンポーネント定義を読み、(1) `...props` があるか (2) 呼び出し側が渡している prop が実際に使われているか を突き合わせる

### lint / build を AC の担保にする前に、該当ルールが error か warn かを確認する
- **問題**: Issue #53 の草案で「未使用コード削除が完了したことを `npm run lint` で担保する」AC を書いたが、LP の ESLint は `no-unused-vars` が **warning 運用（lint は exit 0）** のため、未使用コードが残っていても lint は成功する。AC が実質的に何も検証しない
- **正しい対応**: lint / build / typecheck を AC の担保手段にする場合、対象リポジトリの設定ファイル（`eslint.config.js` 等）で当該ルールの severity を確認する。warn 運用なら「コードレビューで grep 0 件を確認」に変え、lint / build は構文・ビルド回帰の確認として位置づけを分離する

### Codex CLI を起動するときは stdin を /dev/null に繋ぎ、`timeout` は付けない（macOSでは `timeout` が無い）
- **問題1（stdin hang）**: `codex exec -s read-only "{prompt}" > /tmp/out.txt 2>&1` の形で起動した結果、prompt は引数で渡しているにも関わらず codex が stdin を待ち続けて hang し、約1時間28分ブロックして最終的に kill された
- **問題2（timeout で exit 127）**: 上記の対策として `timeout 1200 codex exec ...` を使っていたが、**macOS には `timeout` コマンドが標準で存在しない**（GNU coreutils 非同梱、`gtimeout` も未導入）。その結果 `timeout` が見つからず **exit 127（command not found）で codex が一切実行されず**、サブエージェントが「Codex unavailable / timed out」と誤報告した（issue #2066 の issue-create フローで実際に発生。codex は `/opt/homebrew/bin/codex` に導入済みだった）。
- **正しい対応**: `codex exec --help` の通り「prompt が引数でも stdin が piped なら追加で読み込む」仕様。Bash ツールから起動すると stdin は閉じないため EOF を受け取れず無限待機になる。**必ず以下を全部適用する**:
  1. 末尾に `< /dev/null` を付けて stdin を即 EOF
  2. **`timeout`（および `timeout 1200`）は付けない。** macOS では存在せず exit 127 になる。外側からの強制終了は正常な長時間調査の途中結果も失う。codex 自身の内部 hard cap（約20分）に任せる
  3. Bash ツールは **`run_in_background: true`** で起動する（Bash 前景 timeout 上限は 600000ms = 10分なので、10分超の実行を許容するには background 必須）。完了通知（`status: completed`）を待ってから出力を読む。途中経過の BashOutput で独自に打ち切らない
- **異常判定**: 完了通知が届いた後にのみ判定する。exit 127 は「Codex unavailable（コマンド未検出、PATH確認）」、最終応答（`^codex` ブロック）が無ければ出力末尾のエラー行を返す。途中経過で「timed out」と早とちりしない
- **適用範囲**: ask-codex / issue-update / issue-create / issue-manually-update の各 SKILL で `timeout` 撤去済み（ask-codex は元から `timeout` 禁止だったが他3つが未追随だったのが今回の不整合の原因）
- **再発防止コマンド形**:
  ```bash
  codex exec -s read-only "{prompt}" > /tmp/codex-{task}.txt 2>&1 < /dev/null
  ```

### Codex サブエージェントは sonnet ＋ 同期ブロックで待つ（haiku禁止／完了通知に頼らない）
- **問題**: issue-create の Pre-PR レビューで Codex を `model: "haiku"` サブエージェント ＋ `run_in_background: true` で起動したところ、haiku は codex 起動後に「Monitorで監視中。完了したら抽出して返します」と**途中報告して約11秒（ツール2回）でターンを終了**した。**サブエージェントはバックグラウンドジョブ完了時に再呼び出しされない**（`<task-notification>` で再起動されるのは親＝メインループのみ）ため、codexの最終結果が一切抽出されず永久に失われた（issue #109 対応時、akichim21/shaire）。codex自体は正常で（同時刻の他フローでは数百KBの結果を生成）、原因は完全にオーケストレーション側。
- **根本原因**: `run_in_background:true` の「完了したら再呼び出し」はメインループ向けの仕組み。`Agent` ツールで spawn したサブエージェントはターンを終えると親に最終メッセージを返して終了するだけで、後から再開されない。したがって「待つ」は受動的（通知待ち）ではなく**能動的（同一ターン内で同期ブロック）**でなければならない。
- **正しい対応**:
  1. **モデルは `sonnet`**（haiku は途中で諦めてターンを終える事故が複数回）。
  2. **同一ターン内で同期ブロック**: `run_in_background: true` で起動して task_id を得たら、`TaskOutput({task_id, block: true, timeout: 600000})` を status が completed になるまで繰り返し呼ぶ（codexが20分かかってもループで待てる）。`<task-notification>` の完了通知には頼らない。
  3. **待機中にターンを終了しない**。「監視中」「Monitorで追跡中」「完了したら返します」を最終メッセージにして終わるのは失敗。awk抽出結果を返すまでターンを継続する。
- **適用範囲**: ask-codex / issue-create / issue-update / issue-manually-update / verify-testcases の各 SKILL を「sonnet ＋ 同期 TaskOutput ブロック ＋ ターン終了禁止」に統一済み（2026-06-02）。

### 名前付きチームメイトの報告は SendMessage を呼ばないと永久に失われる
- **問題**: `Agent` ツールに `name` を付けて起動したエージェント（`taskKind: in_process_teammate`）は、最終メッセージがリーダーへ自動的に返らない。2026-08-26 の Issue 作成（tabi #4019 / hotel-infra #170）で、`docs-reviewer` と `req-completeness-checker` の2体がそれぞれ5,000字超の完全なレビューを書き上げながら `SendMessage` を**0回**しか呼ばず、リーダーには idle 通知しか届かなかった。**催促しても直らない**（2体とも催促後に再び無言で idle）。同時起動した `codebase-explorer` は `SendMessage` を1回呼んで届いており、本人も「本文にしか書いておらず届いていませんでした」と認めた
- **正しい対応**:
  1. 起動プロンプトの末尾に「結果は必ず `SendMessage({to: "team-lead", ...})` で送ること。最終メッセージに書くだけでは届かない」を必ず入れる
  2. idle 通知を完了とみなさない。**レポート本文を受け取ったか**で判定する
  3. 催促は1回まで。届かなければ `~/.claude/projects/<project>/<session-id>/subagents/agent-a<name>-*.jsonl` の最後の assistant テキストブロックから直接回収する（`SendMessage` が0回なら本文は確実に残っている）
  4. 回収もできなければリーダー自身が代替実施する。レビュー未実施のまま Issue を作成しない
- **失われかけた内容の重大度**: この2体のレポートには、作成済み Issue を壊す High 指摘が含まれていた。(1) `.circleci/config.yml` の削除行範囲が誤りで、指定どおり消すと孤立した `- run:` が残り YAML が壊れる (2) 本番/staging の PDF 画像化は Lambda 側で完結するため、「staging で PDF をアップロードして確認」は policy 変更の担保にならない。**回収しなければ両方とも Issue に残ったままだった**
