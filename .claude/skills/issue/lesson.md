# Issue Lesson - レビュー指摘パターン集

> このファイルはレビュー指摘や実装中に学んだパターンを記録します。
> Issue の作成・更新ワークフロー時に参照し、同じミスの再発を防ぎます。

## パターン一覧

### E2Eテスト（Playwright）はアクション実行＋結果検証まで含める
- **問題**: PlaywrightのE2Eテストが画面表示の確認（フォーム描画、ボタン状態）だけで終わり、実際のアクション（作成・保存・実行等）を実行して結果を検証していなかった
- **正しい対応**: E2Eテストはユーザー操作の全フローを実行し、結果を後続画面で検証すること。表示確認だけのテストは unit テストに任せる
- **例**:
  - NG: 申請フォームで入力項目の表示だけ確認 → OK: 実際に申請を送信し、完了画面/一覧に反映されたことを検証
  - NG: 管理画面の申請一覧表示だけ確認 → OK: 審査ステータスを変更し、ステータス変更が一覧/詳細に反映されたことを検証
  - NG: サロンポータルのキャンセル請求一覧表示だけ確認 → OK: 請求操作を実行し、ステータス変更を一覧/詳細で検証

### 通知フロー仕様は実装コードと照合してから確定する
- **問題**: Issue仕様に「サロンと顧客の両方にメール／SMS」と記載したが、実装では片方のみだった。仕様と実装の齟齬があるままIssueを作成すると、実装者が誤った方向で作業する
- **正しい対応**: 通知・メール・SMS等のコミュニケーション仕様を書く際は、`cancel-billing-service-api` の該当アクションのサービス層を読み、SES（メール）/ Twilio（SMS）の送信先・送信条件を確認する
- **チェック手順**:
  1. 該当アクションのハンドラ/サービス（`cancel-billing-service-api/src/`）を読む
  2. メール（SES）送信先と SMS（Twilio）送信先、送信トリガー条件を確認
  3. Issue仕様の通知送信先・タイミングが実装と一致しているか照合
  4. 不一致があれば実装に合わせるか、意図的な変更であることを明記

### 既存ドキュメントとの整合性を確認する
- **問題**: Issue仕様がdocs/product/配下の既存ドキュメント（例: cancellation.md）の記述と矛盾していた。具体例: 特定の申請ステータスでは「いつでも操作可能」と既存docsに記載があるのに、新仕様で当該ステータスにも制限を適用する設計になっていた
- **正しい対応**: Issue草案作成後にdocs-reviewerエージェントで既存ドキュメントとの整合性を検証する。矛盾がある場合は、意図的な仕様変更であることを確認事項として明記し、ユーザーに確認する。承認後はdocs更新もスコープに含める

### Issue仕様で参照する関数名は実装コード上の正確な名前を使用する
- **問題**: Issue草案で参照実装の関数名を記憶で書いたところ、実際のロジックは別関数だった。誤った関数参照により実装者が間違ったアルゴリズムを選択するリスクがあった
- **正しい対応**: 仕様に関数名・メソッド名を記載する際は、必ずGrepで実装を確認し、正確な関数名・ファイル名・行番号を記載する。類似名称の関数が複数ある場合は、それぞれの用途の違いを明記する
- **チェック手順**:
  1. 仕様に記載する関数名を `Grep` で検索
  2. 関数の実装を読み、仕様の目的と合致しているか確認
  3. 類似名称の関数が存在する場合は用途の違いを明記する

### 新規作成か既存改修かが曖昧なまま仕様を書いた
- **問題**: 仕様に「〇〇機能を追加する」とだけ書き、新規ページ作成なのか既存ページへの追加なのかを明示しなかった結果、実装者が誤った場所に実装して手戻りが発生した
- **正しい対応**: 仕様には必ず「新規作成」か「既存の○○ページ/バッチの○○部分を改修」かを明記する。曖昧な場合はユーザーに確認する

### AC間の依存関係（テストインフラ前提条件）を明示化する
- **問題**: AC-1.3（一覧テーブルの表示検証）がREQ-2（seedデータに値追加）に暗黙的に依存していたが、依存関係が明記されていなかった。実装者がREQ-1だけ着手しても、seedデータがないためテストが通らない
- **正しい対応**: ACがテストインフラ（seedデータ、環境設定など）に依存する場合、ACに「前提: REQ-Nが完了していること」と明記する。特にPlaywrightテストのseedデータ依存は見落としやすい
- **チェック手順**:
  1. 各ACが検証時にどのデータを必要とするか確認
  2. そのデータが他のREQで作成されるものであれば依存関係を明記
  3. 共有テストインフラ（seed/フィクスチャ）の変更は影響範囲を明記（Playwright/Jest 両方に影響）

### Codex CLI を起動するときは stdin を必ず /dev/null に繋ぐ
- **問題**: `codex exec -s read-only "{prompt}" > /tmp/out.txt 2>&1` の形で起動した結果、prompt は引数で渡しているにも関わらず codex が stdin を待ち続けて hang し、約1時間28分ブロックして最終的に kill された
- **正しい対応**: `codex exec --help` の通り「prompt が引数でも stdin が piped なら追加で読み込む」仕様。Bash ツールから起動すると stdin は閉じないため EOF を受け取れず無限待機になる。**必ず以下の3点を全部適用する**:
  1. 末尾に `< /dev/null` を付けて stdin を即 EOF
  2. `timeout 1200 codex exec ...` で wall-clock 強制終了（codex の hard cap = 20分）
  3. Bash ツールは **`run_in_background: true`** で起動する（Bash 前景 timeout 上限は 600000ms = 10分なので、20分 cap を効かせるには background 必須）
- **適用範囲**: ask-codex / issue-update / issue-create / issue-manually-update の各 SKILL でテンプレ更新済み
- **再発防止コマンド形**:
  ```bash
  timeout 1200 codex exec -s read-only "{prompt}" > /tmp/codex-{task}.txt 2>&1 < /dev/null
  ```
