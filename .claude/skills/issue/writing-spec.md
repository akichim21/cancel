# 詳細仕様の書き方（最重要）

- **画面/機能単位で整理**する（ユースケース単位ではない）。
- **REQ-N番号を各ブロックに付与**する。
- **日本語の散文で記述**する（箇条書きの羅列ではなく文章で）。
- コード参照（ファイルパス、クラス名、関数名等）はインラインに書かず「→ 実装設計を参照」で誘導する。
- 関連ユースケースは簡潔に参照する（「関連ユースケース: UC-1」）。
- **対象アプリを明記する**: 各REQがどのアプリ（スタイリスト/カスタマー/管理画面/サーバー）に関わるか明示すること。
- **変更対象の明示（必須）**: 新規作成（新しいページ / バッチ / API等）か、既存の改修かを明記する。既存改修の場合は、どのページ / バッチ / APIのどの部分に変更を加えるかを具体的に記述する。
- 必須観点:
    a) **表示仕様**: 何をどこにどう表示するか。
    b) **条件分岐・表示ルール**: どの条件でどの表示/挙動になるか。
    c) **バリデーション・エラー処理**: 入力制約、エラー時の表示・挙動。
    d) **操作時の挙動**: ボタン押下・フォーム送信等の振る舞い。

## 具体例

予約詳細画面の場合:

> **[スタイリストアプリ]** 予約詳細画面にキャンセルボタンを表示する。キャンセルボタンはステータスが「確定」の場合のみ活性化し、「キャンセル済み」「チェックイン済み」の場合は非活性（グレーアウト）とする。キャンセルボタン押下時は確認ダイアログを表示し、「はい」選択でキャンセルAPIを呼び出す。API成功時はステータスを「キャンセル済み」に更新し画面を再描画する。API失敗時はエラートーストを表示し画面状態は変更しない。→ 実装設計を参照

## テンプレート

```markdown
## 詳細仕様 (Detailed Specification)

### REQ-1: [画面/機能名] [対象アプリ]
[日本語散文で記述]
→ 実装設計を参照

### REQ-2: [画面/機能名] [対象アプリ]
[日本語散文で記述]
→ 実装設計を参照
```
