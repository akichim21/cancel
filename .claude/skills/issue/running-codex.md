# Codex レビューの回し方（共通手順）

issue-create / issue-update / issue-manually-update の各ワークフローで Codex に草案レビューを依頼するときの共通手順。

## 大原則: Codex は**リーダー（メインエージェント）が直接起動する**

サブエージェントに Codex 起動を委譲してはならない。**サブエージェントはバックグラウンド完了で再呼び出しされない**ためである。ターンを終えた時点で結果が永久に失われる。「同期的にブロックして待て」と指示しても守られない事故が繰り返し起きている（haiku で発生、lesson 参照）。**リーダー（メインループ）は完了通知で再呼び出しされる**ため、この失敗モードが構造的に発生しない。

実際に `req-completeness-checker` へ委譲してレビューが丸ごと欠落した事故がある。加えて `docs-reviewer` のように `Bash` を持たない分析系エージェントもあり、委譲先によっては起動すらできない。

> エージェントが `Bash` を持っているかどうかは委譲してよい理由にならない。判断基準は上記の再呼び出し特性のみである。

## 実行タイミング

草案が完成した直後、**レビューチームメイトの生成と同じターンで**起動する。Codex は 10〜20 分かかるため、チームメイトのレビューと並行させる。

## 手順

### 1. プロンプトをファイルに書き出す

Codex プロンプトは長く、引用符・バッククォート・改行を含むため、**シェルに直接埋め込まない**。スクラッチパッドにファイルとして書き出し、`"$(cat ...)"` で渡す。

```
{scratchpad}/codex-prompt.txt
```

### 2. 出力先は毎回ユニークなパスにする（固定パス禁止）

**固定パス（`/tmp/codex-issue-create-review.txt` 等）を使ってはならない。** 前回の実行や別 Issue の成果物が残り、それを今回の結果として取り込む事故が実際に発生している（領収書 Issue のレビュー中に、別 Issue「プロフィール更新チェックボックス」のレビュー結果が残っていた）。Codex の出力は数百 KB あり、中身を読むまで取り違えに気づけない。

出力先はスクラッチパッド配下に**タスク名＋タイムスタンプ**で作る。

```
{scratchpad}/codex-{task}-{YYYYMMDDHHMMSS}.txt
```

### 3. Bash で起動する（`run_in_background: true`）

```bash
codex exec -s read-only "$(cat {scratchpad}/codex-prompt.txt)" > {出力先} 2>&1 < /dev/null
```

守るべき点:

- **`run_in_background: true` を指定する。** codex は 10 分を超えることがあり、Bash ツールの前景 timeout 上限 600000ms を超えるため必須。
- **stdout をファイルにリダイレクトし、stdin を `/dev/null` に繋ぐ。** これを怠ると codex が stdin 待ちで hang する（数十分〜数時間ブロックした事故あり）。
- **`timeout` コマンドは絶対に付けない。** macOS には標準で存在せず、`timeout 1200 codex ...` は exit 127 になり codex が一切実行されない（実際に発生）。codex 自身の内部 hard cap（約20分）に任せる。
- リーダーは完了通知（`status: completed`）で再呼び出しされる。**待機のためだけにポーリングしない。** 通知が来るまで他の作業（チームメイトの結果統合、草案の自己レビュー）を進めてよい。

### 4. 完了後、最終レスポンスのみを抽出する

Codex の出力には中間のツール呼び出し（rg, sed 等の結果）が大量に含まれる。**出力ファイル全体を Read してはならない**（トークンを浪費する）。

```bash
LAST_LINE=$(grep -n "^codex" {出力先} | tail -1 | cut -d: -f1)
awk "NR>=${LAST_LINE}" {出力先}
```

抽出前に、そのファイルが**今回の実行で作られたもの**であることを確認する（手順2のユニークパスを守っていれば自動的に満たされる）。

### 5. 異常終了の判定

判定は完了通知が届いた後にのみ行う。途中経過を見て「timed out」と早とちりしない。

| 状況 | 扱い |
|------|------|
| exit code 127 かつ最終応答ブロックなし | Codex unavailable（codex コマンド未検出。PATH を確認）。再試行しない |
| その他で最終応答ブロックなし | 出力末尾のエラー行をそのまま報告。再試行しない |
| Codex が利用できなかった | チームメイトのレビュー結果のみで先に進み、**Codex 分が欠落していることをユーザーに明記する** |

## Codex の指摘の扱い

- **Codex の指摘を鵜呑みにしない。** 特に「実装がこうなっている」という事実主張は、**自分でコードを読んで裏を取ってから**草案に反映する（過去に Codex・レビューエージェント双方の事実誤認が実際にあった）。
- 反映した指摘には出典タグを付ける（例: `[~Codex@4a]`）。
- Codex が総合判定 NO-GO を出しても、その根拠が草案側で解消済み・決定事項化済みであれば、その旨を明記して先に進んでよい。
