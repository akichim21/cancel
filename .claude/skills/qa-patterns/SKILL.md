# QA検証パターン設計スキル

## 概要
テストケースの設計・分類・記述に関するベストプラクティス。
Express + AWS Lambda (Node.js) + React 構成で、Jest / Vitest / Playwright を使ったテスト戦略を定義する。

## このスキルを参照すべきタイミング
- 新機能・改修のテストケースを設計するとき
- テストをどのレイヤー（API Unit / API 統合 / Frontend Unit / Playwright）に書くべきか判断するとき
- エッジケースの網羅度を決めるとき
- API 統合と Playwright のどちらで担保するか迷ったとき
- テストケース表をMarkdownで記述するとき
- 同値分割法・境界値分析でテストパターンを導出するとき

**IMPORTANT**
- テストケースに対して、jest, vitest, playwright, 人力どこで担保するのかを改行して明記する
  - 後続にシステムテストすべき項目の一覧を書き出し、そこへの参照だけでも良い。
- 画面仕様(受け入れ条件)については、本来はPlaywrightでテストを限り統合テストできたと判断できないはずである。ただし、複数のUnit test/API 統合/Frontend Unitを組み合わせることで、仕様(受け入れ条件)を満たしたと言えるのでその根拠を明確に記載すること
  - 例えば、他のテストケースでPlaywrightで基本のユースケースは検証できており、サーバーの出しわけとフロントの出しわけだけが違いでリクエストレスポンスが変わらないのであれば、API 統合 + Frontend Unit + 別のテストケースPlaywrightのテストを組み合わせて担保できてるというようなロジックは成り立つ。
- API 統合 + Frontend Unitだけだと結合テストはできてないと判断すること。Playwrightか人間が最終テストをして初めて保証されたとみなします。
  - その際は自動テストで担保できてる部分、人間が担保すべきことをチェックボックスにして内訳のように記載する
- 全て自動テストして欲しいので、人力テストにすべきとした場合、なぜ人力でないとできないか理由も明記すること
- 人間がテストすべきことはわかりやすく明記すること
