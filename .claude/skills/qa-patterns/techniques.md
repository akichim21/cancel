# テストケース設計技法

## 1. 同値分割法（Equivalence Partitioning）

入力値を「同じ振る舞いをするグループ（同値クラス）」に分割し、各クラスから代表値を1つ選んでテストする。

**目的：** テスト数を削減しつつ網羅性を確保する。

**適用例：キャンセル請求件数入力フィールド（1〜10が有効）**

| 同値クラス | 範囲 | 代表値 | 期待結果 |
|-----------|------|--------|---------|
| 無効（下限未満） | ≤ 0 | -1 | バリデーションエラー |
| 有効 | 1〜10 | 5 | 正常処理 |
| 無効（上限超過） | ≥ 11 | 20 | バリデーションエラー |
| 無効（型不正） | 文字列・null | "abc", null | バリデーションエラー |

**適用の指針：**
- API Unit Testで網羅する（各同値クラスから最低1つ）
- API 統合 / Playwrightでは有効クラスの代表値のみ使用
- 同値クラスの分割はビジネスルールから導出する（仕様書・コード両方を確認）

---

## 2. 境界値分析（Boundary Value Analysis）

同値クラスの境界で不具合が発生しやすいため、境界上とその前後の値をテストする。

**適用例：キャンセル請求件数入力フィールド（1〜10が有効）**

| # | テスト値 | 位置 | 期待結果 |
|---|---------|------|---------|
| 1 | 0 | 下限境界 -1 | エラー |
| 2 | 1 | 下限境界（有効） | 正常 |
| 3 | 10 | 上限境界（有効） | 正常 |
| 4 | 11 | 上限境界 +1 | エラー |

**適用の指針：**
- API Unit Testで必ず実施（全境界値をカバー）
- 数値だけでなく、文字列長、配列サイズ、日付範囲にも適用する
- API 統合では主要な境界値のみ（上限・下限の各1ケース程度）

---

## 3. 同値分割法 + 境界値分析の組み合わせ

実務では両方を組み合わせてテストケースを導出する。

```
1. 仕様からビジネスルールを抽出
2. 入力値を同値クラスに分割
3. 各同値クラスの境界値を特定
4. 代表値 + 境界値でテストケースを生成
```

**例：キャンセル請求件数（1〜10件、まとめ割引は5件以上）**

| # | 同値クラス | テスト値 | 境界 | 期待結果 |
|---|-----------|---------|------|---------|
| 1 | 無効（下限未満） | 0 | 下限-1 | エラー |
| 2 | 有効（通常料金） | 1 | 下限 | 正常・通常料金 |
| 3 | 有効（通常料金） | 4 | 割引境界-1 | 正常・通常料金 |
| 4 | 有効（まとめ割引） | 5 | 割引境界 | 正常・まとめ割引適用 |
| 5 | 有効（まとめ割引） | 10 | 上限 | 正常・まとめ割引適用 |
| 6 | 無効（上限超過） | 11 | 上限+1 | エラー |

---

## 4. テストケース設計の手順

新機能・改修のテストケースを設計する際は、以下の手順で進める。

```
1. 仕様からビジネスルールを抽出
2. 入力値に同値分割法を適用し、同値クラスを特定
3. 各同値クラスの境界値を特定（境界値分析）
4. 状態遷移がある場合、全遷移パスを列挙
5. 優先度マトリクス（P0/P1/P2）で各ケースを分類
6. テストレイヤーに振り分け:
   - ロジック・境界値・同値クラス → API Unit Test (Jest unit)
   - ハンドラの契約・認証認可 → API 統合 Test (Jest handler integration)
   - コンポーネント・表示ロジック → Frontend Unit Test (Vitest)
   - Web 画面のUI統合 (user / admin / lp) → Playwright E2E
   - デザイン・UX・外部API連携 → 手動検証
7. テストケース表をフォーマットに従って記述（→ bestpractice.md §6）
8. 回帰への影響を明示
```
