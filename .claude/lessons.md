## 全般

### issue-start完了前にテスト一覧を全チェックする
- **問題**: Issue受け入れ条件のテスト一覧(T-1〜T-25等)のうち、一部のテストを実装せずにCompletionコメントを投稿した。Jest（API）/Vitest Unit、Playwrightテストの一部が未実装だった。
- **正しい対応**: 実装完了前に受け入れ条件のテスト一覧を1行ずつ確認し、全テスト項目に対応するテストファイルが存在すること・実行してgreenであることを検証する。チェックリストをgrepで機械的に確認する。
- **チェック手順**:
  1. `gh issue view` でIssueのテスト一覧を取得
  2. 各T-NのテストIDに対応するテストファイルを `grep` で検索
  3. 未実装のテストIDがあれば実装する
  4. 全テスト実行してgreenを確認
  5. `gh issue edit` でチェックボックスを更新
  6. その後に[Completion]コメントを投稿する（順序厳守）

### テスト実行→issue更新→Completionコメントの順序を守る
- **問題**: テスト実行やissueチェックボックス更新をせずにCompletionコメントを先に投稿した。
- **正しい対応**: 必ず「テスト全green確認 → issueチェック更新 → Completionコメント投稿」の順序を守る。Completionコメントは最後の最後に投稿する。

### UIバグのデバッグは「APIは正しいか」と「表示は正しいか」を分離して検証する
- **問題**: UIに×が表示されている時、サーバー側のバグなのかクライアント側のレンダリングの問題なのか区別せずにデバッグして時間を浪費した。
- **正しい対応**:
  1. **まずAPIレスポンスを直接確認** (curl等) — サーバーが正しいデータを返しているか
  2. **APIが正しい場合、クライアント側のデータフローを追跡** — store/hooks/componentの各段階でデータがどう変換されるか
  3. **スクリーンショットとDOMで実際の表示を確認** — テストが通っても表示が正しいとは限らない
- **原則**: API・状態管理・レンダリングなど複数レイヤーにまたがる問題は、各レイヤーを独立して検証しないと原因特定できない

### 複雑なUI（カレンダー・グリッド等）のデバッグではDOMを必ず確認する
- **問題**: Playwrightテストのアサーションが通っているのに、実際のUIが期待と異なっていた。ラベルの存在確認だけで「セルが正しく表示されている」と誤判断した。
- **正しい対応**:
  1. Playwright の `page.content()` / locator スナップショットで実際のDOM・テキスト・表示状態を確認する
  2. `page.screenshot({ path: '/tmp/debug.png' })` でスクリーンショットを取り、目視で確認する
  3. テストアサーションが**本当に検証したいこと**をassertしているか確認する（ラベルの存在 ≠ セルが正しい値）
- **原則**: カレンダー、テーブル、データグリッドなど複雑なUIでは「テスト通った→OK」と判断せず、DOMとスクリーンショットで裏取りを必ず行う

### ステータスのフィルター条件はドメインのライフサイクル全体を考慮する
- **問題**: 予約の満席判定で `confirmed` と `requested` のみカウントし、`completed`（決済完了）を含めなかった。ローカルのseedデータはconfirmedのみで動作するが、本番/dev環境では大半がcompletedのため満席にならなかった。
- **正しい対応**: ステータスでフィルター/カウントする際は、エンティティのライフサイクル全ステータスをレビューする。特に「テスト環境では特定ステータスだけで動作確認できてしまう」ケースに注意。実環境の典型的なデータ分布を想定して検証する。

### リスト要素の key には行のユニーク値を含める
- **問題**: ページ切替で描画内容が変わるリストUIで `key={index}` を使うと、React が DOM を再利用し props 更新を飛ばして「表示されている値」と「内部状態」がずれるバグが発生する。
- **正しい対応**:
  1. **`key` には行のユニーク値を含める**: `key={index}` ではなく `key={\`${id}-${date}\`}` のように、同じリスト内で衝突しない安定キーを使う
  2. **メモ化の比較関数は全 props を比較する**: `React.memo` の `areEqual` はレンダリング結果に影響する全フィールドを比較する。一部だけ比較すると stale reuse の温床になる
- **検証方法**: DOM スナップショットから各行の data 属性を抽出し、表示値と内部状態の値を比較する。スクリーンショットだけでは内部状態のずれは見えない

### Codex exec のバックグラウンド実行は完了通知を待ってから出力を読む
- **問題**: `codex exec` をバックグラウンドで実行し、完了通知が来る前に出力ファイルを `tail` で確認。中間のファイル読み込み結果しか見えず「Codexがレビュー結果を出力できなかった」と誤判断した。実際には最終レスポンスがファイル末尾に正常に出力されていた。
- **正しい対応**:
  1. `run_in_background` で起動したタスクは **完了通知が来るまで出力ファイルを読まない**
  2. 完了後、Codex出力の最終レスポンスは `grep -n "^codex" {output} | tail -1` で最後のアシスタントターンの行番号を取得し、そこから末尾を読む
  3. Codexのファイル読み込み（rg, sed等）はレビュー品質を上げるための正当な行動であり、ノイズではない
  4. `codex exec` の出力ファイル自体は親Claudeのコンテキストに自動流入しない。**トークンを消費するのは親Claudeが `Read`/`tail` で出力ファイルを読みに行った時だけ**

### Codex exec はhaiku サブエージェント経由で実行し、stdout はファイルにリダイレクトする
- **問題**: `codex exec` の出力には中間のツール呼び出し結果（rg, sed出力）が大量に含まれる。親Claudeが直接 `Read`/`tail` するとトークンを浪費する。サブエージェント内でも Bash の戻り値として受け取ると同様にトークンを消費する。
- **正しい対応**:
  1. `model: "haiku"` のサブエージェントで実行する
  2. `codex exec ... > /tmp/codex-review.txt 2>&1` で **stdout をファイルにリダイレクト**し、Bash の戻り値としてサブエージェントのコンテキストに入れない
  3. 完了後、`grep -n "^codex" | tail -1` + `awk` で最終レスポンスのみを抽出
  4. 抽出結果のみを親に返す。出力ファイル自体を `Read` しない
- **結果**: 親もサブエージェントも中間出力のトークンを消費しない。SKILLの Step 7 参照。

### バグ修正の切り分けは git show + revert + red/green で行う
- **問題**: コード修正が本当にバグに効いているのか、コードレビューだけでは確信が持てなかった。
- **正しい対応**:
  1. `git show <commit>` で修正内容を理解し、症状との因果関係をコード上で説明する
  2. 対象ファイルだけを `git show <commit>^:<path>` で一時的に revert する（worktree 全体を戻さない）
  3. revert 状態で E2E テストを実行 → **red** を確認
  4. 修正を戻して同じテストを実行 → **green** を確認
  5. 差異が明確なら「修正が効いている」と断言できる
- **注意**: revert は最小限のファイルだけ行い、終了後は必ず `git checkout -- <files>` でcleanに戻す

### E2E のテスト用分岐を production code に入れない
- **問題**: 入力 flake などに対して `ENV_NAME` 分岐や test 専用デフォルト値を production code に入れると、bundle に test 用ロジックが混ざり、E2E が本来検証すべき「ユーザーが入力する」操作を飛ばしてしまう
- **正しい対応**: 入力は Playwright 側で実行したまま、`waitFor` / 再試行 / 自動スクロールを使って安定化する。production 側で default を入れず、テストコード側で安定化する

### import boundary の回帰は smoke import テストで防ぐ
- **問題**: 遅延読み込みするモジュールは循環依存があると実行時だけ `default of undefined` 等で落ち、通常の render test では見逃しやすい
- **正しい対応**: 修正時は禁止 import のソース検査と `await import(...)` の smoke import を追加し、構造的に再発を防ぐ

### サブエージェントの cross-file 指摘は必ず再検証する
- **事例**: hotel PR #1938 で submit ボタン非表示ロジックを親コンポーネント (`BookingForm.tsx`) だけ読んで「消えない」と誤指摘し、そのまま行コメント投稿してしまった。
- **原因**: 描画層が子コンポーネント (`BookingStepFormSecond.tsx` の `showBlockedGuide` 判定) に委譲されていることを見逃した。サブエージェントが onSubmit ハンドラーだけを読み、JSX レンダリング層 / 子コンポーネントを追跡しなかった。
- **対策**: `.claude/skills/review-verification/SKILL.md` の cross-file 検証チェックリストに従い、呼び出しチェーン / 親子コンポーネントを追跡してから指摘を確定する。UI 挙動・認可・バリデーション・コールバック・委譲に関する指摘は、メインエージェント側でも投稿前に再検証する。
