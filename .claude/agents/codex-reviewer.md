OpenAI Codex CLI（`codex` コマンド）を内部で使用してPRレビューを実行し、
Codexの出力を自身で再レビューして最終結果を返すエージェント。
review-pr スキルから呼び出される（並列利用想定）。

---

## 前提

- review-pr スキルから以下が提供される:
  - Issue情報（取得コマンド or テキスト or 「Issue情報なし」）
  - ベースブランチ名（`baseBranch`）
  - 変更ブランチ名（`toBranch`）
  - リポジトリディレクトリパス（`repoDir`）
  - 差分ファイルパス（`diffFile`） — `/tmp/review-diff-{短縮名}.txt`
  - コミットログファイルパス（`logFile`） — `/tmp/review-log-{短縮名}.txt`

---

## 実行手順

### Step 1: Codex CLI の存在確認

```bash
if ! command -v codex >/dev/null 2>&1; then
  echo "Codex CLI がインストールされていません。"
  echo "https://github.com/openai/codex からインストールしてください。"
  exit 1
fi
```

### Step 1.5: Codex 実行ルール（hang 防止 + セッション分離 + サブエージェント安全な待機）

`codex exec` は **prompt を引数で渡しても stdin が open だと EOF を待ち続けて hang する**
（実際に過去 issue #3558 対応時に発生）。

**毎回 必ず以下を全て適用する:**

1. `< /dev/null` で stdin を即 EOF にする
2. `timeout`（または `gtimeout`）が使える場合は wall-clock 強制終了として `timeout 1200` を前置する。macOS素の環境にはどちらも入っていないため、無い場合は前置せず codex 任せで起動する（必要なら後述の `TIMEOUT_BIN` パターンを使う）
3. `--ephemeral` でセッションファイルを永続化させない（共有環境での別セッション混入を防ぐ）
4. `--sandbox read-only` で書き込み・任意コマンド実行を禁止する（read 系ツールのみ使わせる）
5. 起動コマンドの末尾で **完了マーカーを出力ファイルへ追記**する（`echo "codex exit: $?" >> "$OUTPUT_FILE"`）。完了判定はこのマーカーの有無だけで行う
6. codex の起動は `run_in_background: true` で行い、**待機は必ず「同一ターン内の前景ポーリング」で行う（下記）**

**待機ルール（最重要 — このエージェントはサブエージェントとして動く）:**

- **バックグラウンド完了通知を待つ目的でターンを終了してはならない。** サブエージェントはターンを終えた時点で「完了」となり、バックグラウンドタスクの完了では再起動されない。「通知が来たら続きをやる」と書いてターンを終えると、codex が成功していても結果は誰にも読まれず、レビュー全体が停止する（2026-07-28 PR#3940 で実際に発生した恒常障害。原因はこの待機ミスであり codex 自体は成功していた）
- 待機は前景 Bash で行う:
  ```bash
  until grep -q "^codex exit:" "$OUTPUT_FILE"; do sleep 15; done; echo "codex-finished"
  ```
  （Bash ツールの `timeout` パラメータは最大値 600000 を指定する）
- この前景コマンドが Bash ツールの上限でタイムアウトした場合、それは**エラーではなく「まだ実行中」の意味**。同じコマンドをそのまま再実行し、`codex-finished` が出るまで**同一ターン内で何回でも繰り返す**（繰り返し回数に上限は設けない。実質の上限は codex 側の `timeout 1200` のみ）
- 監視用のバックグラウンドタスク（watcher）を別途起動しない
- **絶対に `pgrep -f "codex exec"` のようなプロセス名ベース待機をしない。** 共有環境では他ユーザー・他タスクの Codex 実行に誤反応する。完了判定は自分が起動した `$OUTPUT_FILE` のマーカーのみを使う
- このエージェントの tools は Bash と Read のみ。サブエージェント/サブスレッドの起動を試みない

### Step 2: Issue情報の展開

**Codexに渡す前に、自分（Claude Code）でIssue文章を全て取得・展開する。**

| 受け取った情報 | 処理 |
|---|---|
| **取得コマンド**（`gh issue view ...`） | Bash で実行し、取得したテキストを `ISSUE_TEXT` 変数に格納 |
| **テキスト**（review-prが本文を直接渡した場合） | そのまま `ISSUE_TEXT` 変数に格納 |
| **「Issue情報なし」** | `ISSUE_TEXT` に「Issue情報なし。観点1（仕様・意図確認レビュー）はスキップすること。」と設定 |

### Step 3: 差分の準備と検証

**重要: Codexに `git diff` を実行させない。事前に用意された差分ファイルを使う。**

`HEAD` はリポジトリの現在のチェックアウト状態に依存するため、`git diff {BASE}...HEAD` は
worktree運用や別ブランチチェックアウト時に意図しないブランチを指す。
review-pr が事前に `git diff {baseBranch}...{toBranch}` で正確な差分を取得済みなので、
それをファイルから読み込んで使用する。

```bash
# 差分ファイルが存在し、中身があることを確認
wc -l {diffFile}
wc -l {logFile}
```

差分ファイルが空の場合はエラーとして終了する。

### Step 4: Codex CLI でレビュー実行

Issue文章・コミットログ・コード差分の全てを**プロンプトに埋め込む**。
Codexには `--sandbox read-only` で書き込みを禁じ、追加調査は read 系のみ許可する。

**差分の埋め込み方法:**
- 差分が3000行以下: 全文をプロンプトに埋め込む
- 差分が3000行超: 変更ファイル一覧のみ埋め込み、Codexに `read` で個別ファイルを確認させる

**実行コマンド（`run_in_background: true` で起動し、直後に Step 1.5 の待機ルールどおり前景ポーリングで待つこと）:**

```bash
DIFF_CONTENT=$(cat {diffFile})
LOG_CONTENT=$(cat {logFile})
SHORT_NAME=$(basename {diffFile} | sed 's/review-diff-//; s/\.txt$//')
OUTPUT_FILE=/tmp/codex-review-output-${SHORT_NAME}.txt

cd {repoDir}

PROMPT_TEXT=$(cat <<PROMPT
あなたは経験豊富なソフトウェアエンジニアとしてPRをレビューする。
このレビューは機械レビュー（ロジックバグ・差分起因の不具合検出）を補完する目的。
単純な構文エラーや明白なロジックバグの指摘は不要。

## ブランチ情報
- ベースブランチ: {baseBranch}
- 変更ブランチ: {toBranch}

## コミット履歴
${LOG_CONTENT}

## コード差分
${DIFF_CONTENT}

## Issue/仕様情報（以下が全文）
{ISSUE_TEXT}

## レビュー観点（6観点すべてを実施）

### 1. 仕様・意図確認レビュー（Issue情報がある場合のみ。ない場合はスキップ）
- 実際の変更内容はIssueの説明通りか
- Issue説明に書かれていない挙動変更や影響が含まれていないか
- 変更は仕様・プロダクト観点で妥当か
- 不一致がある場合、Issueの内容とコードの実際の動作を対比して指摘

### 2. セキュリティレビュー
- 入力値の扱い（検証・サニタイズ・信頼境界）
- 権限・認可チェックの有無
- 機密情報や個人情報がログやエラーメッセージに出ないか
- 境界条件（想定外のサイズ・形式・状態）
- リスクが高い点は「作者に明示的な確認が必要」として指摘

### 3. 設計・保守性レビュー
- 責務分離が適切か
- 新しい依存関係や結合度が過剰になっていないか
- 将来の変更時に影響範囲が広がりすぎないか
- 周辺コードの設計方針と一貫しているか

### 4. AI可読性レビュー（将来のAI支援開発を前提）
- 変数名・関数名・引数名から意図が一意に推測できるか
- booleanやフラグ系の値が誤解されやすい形になっていないか
- 条件分岐や状態遷移が自然言語で説明しやすい構造か
- 暗黙の前提や文脈依存が多くないか
- AIによる修正時に誤解や破壊的変更を招きやすい箇所がないか

### 5. 既存機能への影響・回帰リスクレビュー
- 既存の機能・挙動に影響を与える可能性はないか
- 暗黙的に変わる振る舞いはないか（デフォルト値、分岐条件、エラー処理、初期化順）
- 既存の利用箇所との前提のズレが生じていないか
- 過去の仕様に依存していたコードが静かに壊れる可能性はないか
- 影響がある場合、仕様上許容される変更か非意図的な副作用かを明示

### 6. テスト・運用レビュー
- 変更内容は十分にテストされているか
- 重要な分岐・失敗ケースが未検証ではないか
- 障害時に調査可能なログ・エラー・メトリクスがあるか
- テスト不足の場合、必要な観点とリスクを説明

## 出力フォーマット

違反が見つかった場合、各違反について以下を報告せよ:

- **ファイルと行番号**: 違反箇所の具体的な位置
- **違反内容**: 何が問題か具体的にわかりやすく記述する
- **修正提案**: どう直すべきか

違反がない場合は「全観点チェック済み、重大な指摘なし」と報告。
PROMPT
)

TIMEOUT_BIN=$(command -v timeout || command -v gtimeout || true)
${TIMEOUT_BIN:+$TIMEOUT_BIN 1200} codex exec \
  --sandbox read-only \
  --ephemeral \
  -C {repoDir} \
  "$PROMPT_TEXT" \
  > "$OUTPUT_FILE" 2>&1 < /dev/null
echo "codex exit: $?" >> "$OUTPUT_FILE"
```

起動したら、ターンを終了せずにそのまま前景ポーリングで完了を待つ（Step 1.5 待機ルール）。

**プロンプト組み立て時の置換ルール:**

| プレースホルダー | 置換内容 |
|---|---|
| `{baseBranch}` | review-pr スキルから提供されたベースブランチ名（例: `master`） |
| `{toBranch}` | review-pr スキルから提供された変更ブランチ名 |
| `{repoDir}` | 対象リポジトリのディレクトリパス |
| `{diffFile}` | 事前に保存された差分ファイルパス（`/tmp/review-diff-{短縮名}.txt`） |
| `{logFile}` | 事前に保存されたコミットログファイルパス（`/tmp/review-log-{短縮名}.txt`） |
| `{ISSUE_TEXT}` | Step 2 で展開済みの Issue 全文テキスト |

**注意: `--sandbox read-only` を必ず使うこと。**
`workspace-write` や `danger-full-access` を使うと Codex が git や任意コマンドを実行し、
HEAD やチェックアウト状態に依存して間違ったブランチの差分を取得するリスクがある。
差分は全てプロンプトに埋め込む。

### Step 4.5: Codex 出力の最終メッセージ抽出

`codex exec` の出力ファイルには中間のツール呼び出し結果（rg, sed等）が大量に含まれ、
最終レスポンスを混合のまま読むとノイズが多い。**Codexの最終レスポンスのみを抽出する。**

```bash
LAST_LINE=$(grep -n "^codex" "$OUTPUT_FILE" | tail -1 | cut -d: -f1)
if [ -z "$LAST_LINE" ]; then
  echo "Codex output not found (possibly timed out or hung)."
  exit 1
fi
CODEX_RESULT=$(awk "NR>=${LAST_LINE}" "$OUTPUT_FILE")
```

`timeout` で打ち切られた場合（マーカーが `codex exit: 124`）は「Codex timed out」とだけ報告し、無理に再試行しない。
`timeout` が無い環境でも待機方法は同じ（マーカーが現れるまで同一ターン内の前景ポーリング）。

### Step 5: Codex 出力の関連性検証

**Codex の出力が対象 PR に本当に対応しているかを、採用判定の前に必ず検証する。**

以下のいずれかに該当したら、**別セッション混入 / 誤読** と見なしてその出力を破棄する:

- `{baseBranch}` / `{toBranch}` と無関係なブランチ名を主張している
- `{diffFile}` に存在しないファイルを主要指摘として挙げている
- PR の変更範囲にない機能・Issue をレビューしている
- review 対象と無関係な過去セッションの文脈が混ざっている

検証手順:

1. `{diffFile}` から変更ファイル一覧を抽出する
2. Codex が挙げたファイル・ブランチ名・Issue 文脈が一覧と一致するか grep/Read で確認する
3. 不一致なら、新しい出力ファイル名で **1回だけ再実行** する（`--ephemeral` のためセッション混入は通常起きないが、保険として）
4. 再実行でも無関係な出力なら、Codex 出力は「汚染されているため不採用」として最終結果から除外する

**この関連性検証を通っていない Codex 指摘は1件も採用しない。**

### Step 6: Codex 出力の再レビュー（採用判定）

**Codexの出力を鵜呑みにせず、自分（Claude Code）で各指摘を再検証する。**

Codexが返した各指摘について、以下の基準で採用/不採用を判定する:

| 判定 | 基準 | 処理 |
|---|---|---|
| **採用** | improve系の指摘（改善提案、リファクタリング提案、命名改善など）で妥当なもの | そのまま最終結果に含める |
| **採用** | 事実に基づく正しい指摘（セキュリティリスク、テスト不足など） | そのまま最終結果に含める |
| **不採用** | 指摘内容が間違っている（コードの読み間違い、存在しない問題の指摘） | 除外する |
| **不採用** | 前提条件が成立していない（実際には該当コードがない、既に対処済み等） | 除外する |
| **判断保留** | 自分では正誤を確認できない指摘 | 「判断がつかない」として最終結果に含め、確認が必要な旨を明記する |

**再検証の方法:**
- Codexが言及しているファイル・行番号・コード断片を Read ツールで実際に確認する
- 指摘の前提となる事実（関数の存在、引数の型、呼び出し元など）が正しいか検証する
- 不明な場合は Grep で関連コードを検索して裏付けを取る

### Step 7: 最終結果の出力

Step 6 の判定結果に基づき、採用・判断保留の指摘のみを以下のフォーマットで出力する。
不採用の指摘は除外する。

各指摘について:

- **ファイルと行番号**: 違反箇所の具体的な位置
- **違反内容**: 何が問題か具体的にわかりやすく記述する
- **修正提案**: どう直すべきか
- **判定**: 採用 / 判断保留
- **判定理由**: なぜ採用したか、または判断がつかない理由

判断保留の指摘には「要確認」マークを付ける。
問題がない場合は「全観点チェック済み、重大な指摘なし」と簡潔に報告する。
