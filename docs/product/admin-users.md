# 管理者ユーザー（運営アカウント）の管理

運営管理者（`users` テーブル / `role='admin'`）のアカウントを**管理画面から一覧・作成・更新する**
仕組み（GTSS-72 / #72）。パス `/admin-users`。

## なぜ画面から管理するのか

以前は運営管理者を作る手段が **CLI スクリプトのみ**だった（`scripts/upsert-admin-user.ts` を
`NODE_ENV=prod AWS_PROFILE=... npx tsx` で人手実行）。増員・退職対応のたびに手作業と本番 DB 接続が要り、
運用が属人化していた。加えて同スクリプトはパスワードを平文で引数・環境変数から受け取るため、
発行したパスワードを人づてに伝える運用になっていた。

画面 + メールリンクへ移すことで、**平文パスワードが第三者（作成した運営者）を経由しない**。
退職者の締め出しも DB 直操作なしで行える。

## 基本方針

- **パスワードは管理画面の入力欄では設定させない。** 作成・編集フォームにパスワード欄は存在しない。
  本人がメールのリンクから設定する。
- **削除（物理・論理とも）は行わない。** 無効化のみで行は残す（運営通知の宛先解決や監査の追跡を壊さないため）。
- **ロールは `admin` 固定。** 画面にロール選択は出さない。RBAC は未実装。
- 無効化・パスワード変更は**即時反映**される（`requireAdmin` が DB を引く。`docs/tech/auth.md`）。

## ライフサイクル

```
[招待]                [設定]                    [運用]        [無効化]         [再有効化]
管理者を追加  →  設定メールのリンクから  →  ログインして  →  ステータスを  →  ステータスを
（有効/未設定）    本人がパスワード設定       利用             「無効」へ        「有効」へ
                   （有効/設定済み）                          （即座に 401）    （**要再ログイン**）
```

### 1. 招待（運営が新しい管理者を追加する）

1. ヘッダーの「管理者ユーザー」→「管理者を追加」
2. 氏名・メールアドレスを入力して保存（パスワード欄は無い）
3. 一覧に「有効 / 未設定」の行が増え、本人宛に**パスワード設定メール**が届く

この時点では `password` が NULL なので**ログインできない**（設定メール本文にもその旨を明記している）。
メール送信に失敗しても管理者レコードとトークンは残るため、編集画面から再送できる。

### 2. パスワード設定（招待された本人）

メールのリンク（`{管理画面}/set-password?token=...`）を開き、新しいパスワードを設定する。
**リンクは 1 回きり・有効期限 24 時間。** 期限切れ・使用済みの場合は他の管理者へ再送を依頼する。

### 3. 運用中

- **自分のパスワード変更**: ヘッダー右上のアバター →「パスワード変更」（`/change-password`）。
  成功しても画面に留まり、ログアウトしない。**変更前に発行した自分の他セッションは失効する。**
- **パスワードを忘れた**: ログイン画面の「パスワードを忘れた方はこちら」（`/forgot-password`）。
  メールアドレスを送ると再設定リンクが届く。
  **画面表示は、アカウントが存在してもしなくても常に同じ**（アカウント列挙対策）。
- **運営が再設定メールを送る**: 編集モーダルの送信ボタン。
  対象がパスワード未設定なら「設定メール」、設定済みなら「再設定メール」を自動で出し分ける。
  **送っただけでは現在のパスワードは無効にならない**（リンクから新パスワードを設定した時点で置き換わる）。
  一方で**以前に送ったリンクはその時点で無効になる**。

### 4. 無効化（退職者の締め出し）

編集モーダルでステータスを「無効」にする。

- 対象が保持していたログイン中のセッションは**次の API リクエストで 401** になりログイン画面へ戻る
- 以後ログインもできない（403「このアカウントはまだ有効化されていません」）
- 未使用のパスワード設定リンクも同時に無効化される
- **運営宛の通知メール（新規申請通知・Stripe 登録完了通知など）の宛先からも外れる。**
  これらの通知にはサロンの事業者名・代表者名・メールアドレス等の個人情報が含まれるため、
  無効化済みの宛先を残すことは個人情報の継続的な送信にあたる

**拒否される操作**:

| 操作 | 挙動 |
|---|---|
| 自分自身を無効化する | 画面ではステータス欄が非活性。API も 400 で拒否 |
| その操作で有効な管理者が 0 人になる | 400 で拒否（2 人が互いを同時に無効化する競合も防ぐ） |

### 5. 再有効化

無効化済みの行は**一覧から消えない**ので、編集からステータスを「有効」へ戻せる。
ただし**旧トークンは復活しない**（無効化時に失効基準時刻を更新するため）。本人は再ログインが必要で、
その際は「パスワードが変更されています。再度ログインしてください」が返る。パスワード自体は
変わっていないが、「再ログインで復帰できる」ことを伝える区別として意図どおりの文言。

## 一覧画面の見方

| 列 | 内容 |
|---|---|
| 氏名 | 未設定（CLI 作成の既存行など）は「—」 |
| メールアドレス | 保存時に前後の空白を除去し小文字へ正規化される |
| ステータス | 有効（緑）/ 無効（灰）。**無効も一覧に表示し続ける** |
| パスワード | 設定済み（緑）/ 未設定（黄）。**ハッシュ値は返さない**（設定済みか否かのみ） |
| 作成日時 | JST 表示 |
| 操作 | 編集（作成と同じモーダルを編集モードで開く） |

## 入力ルール

| 項目 | ルール |
|---|---|
| 氏名 | 前後の空白を除いて 1〜100 文字（空白のみは不可） |
| メールアドレス | 形式（LP の申請フォームと同一）・255 文字以内。**重複は 409 で拒否** |
| ステータス | `有効` / `無効` のみ。作成時は常に「有効」 |

メールの重複判定は**保存済みの値と入力値を双方とも小文字化して比較**する。既存行側に大文字が
含まれていても検出できるようにするため（例: 既存 `Ops@Example.com` と入力 `ops@example.com` は重複）。

## 緊急復旧

全管理者が締め出された場合など、画面から復旧できないときは CLI を使う。

```bash
cd cancel-billing-service-api
NODE_ENV=prod AWS_PROFILE=cancel-billing-service-prod npx tsx scripts/upsert-admin-user.ts
```

**第一手段は管理画面。** CLI は緊急復旧手段として残している。
