# キャンセル請求フロー

サロンの顧客がドタキャンした際の請求〜回収フロー。請求の作成経路は 2 通り:
- **手動作成**: 運営/サロンが管理画面・ポータルから登録（従来）。作成と同時に送信（決済リンク通知）。
- **サロンボード取り込み**: サロンボードからキャンセル予約を自動取り込み、「送信前」で作成し、確認後に送信（GTSS-817）。
  業務詳細は `docs/product/salonboard-import.md`、技術は `docs/tech/salonboard-import.md`。

## 全体フロー

```
[手動登録] または [サロンボード取り込み（送信前で作成）]
    ↓
[（送信前の場合）一覧の「送信」ボタンで内容確認・キャンセル料調整]
    ↓
[顧客にメール/SMSで決済リンク送信] → ステータス: 請求中(pending)・初回送信日時と送信履歴を記録
    ↓
[未払いなら 7日目・14日目の正午に自動リマインド（GTSS-886。下記「自動リマインド送信」）]
    ↓
[顧客が /pay 短縮リンク → Stripe Checkoutで決済（支払期日 = リンク有効期限）]
    ↓
[Stripe Webhook (checkout.session.completed) で完了通知] → ステータス: 支払済(paid)
    ↓
[サロンへpayout (Stripe Connect)]
```

## ステータス（SSOT）

DB 保存値は英語 enum、表示は日本語ラベル（`cancel-billing-service-api/src/constants/cancellation-status.ts`）:

| 値 | ラベル | 意味 |
|---|---|---|
| `pre_send` | 送信前 | 取り込みで作成・未送信（GTSS-817） |
| `pending` | 請求中 | 送信済み・未決済（旧 `sent` を統合） |
| `paid` | 支払済 | 決済完了 |
| `canceled` | キャンセル済 | 取消 |
| `failed` | 失敗 | 決済失敗 |

> **支払済（`paid`）は Stripe webhook（実決済）でのみ到達**し、`paidAt`（支払日）が設定される。管理画面の手動ステータス
> 更新で扱えるのは `pending`（請求中）/ `failed`（失敗）/ `canceled`（キャンセル済）のみで、**手動「支払済」遷移は廃止**
> （GTSS-836 / #30）。手動で支払済にすると `paidAt` 不在のまま精算用CSV・支払日フィルタから漏れるため。

## ステップ詳細

### 1. キャンセル請求の作成

- 手動: 管理画面 `cancel-billing-service-admin/src/components/CancellationManagement.tsx` /
  サロン向け `cancel-billing-service/src/components/InvoiceForm.tsx`。作成と同時に送信。
  - **店舗は登録済み店舗から select**（GTSS-817 #27）。店舗名・住所のフリーテキスト入力は廃止し、自社の
    登録済み店舗（店舗マスタ）を選んで `shopId` を送る。
  - 店舗が **0 件**のときは入力欄を出さず「店舗を作成してください」の文言と**施設（店舗）管理画面へのリンク**を
    表示し、請求は作成できない。
  - サーバは `shopId` を自社店舗として解決し、`cancellations.shopId` に紐づけたうえで、作成時点の
    **店舗名・住所をスナップショット**（`shop_name` / `shop_address`）として保存する。
  - 旧形式（`shopName` フリーテキストのみ）のリクエストは **400 で拒否**（即時撤去・後方互換なし）。
  - **送信方法の推奨は「SMSとメール」**（GTSS-896）。サロンポータルの請求作成フォームでは「SMSとメール」の
    右隣に緑の「推奨」バッジを出す。**既定の選択は `SMS` のまま**（既定を「SMSとメール」にすると開いた直後から
    電話番号欄とメールアドレス欄の両方が必須になり、片方しか連絡先が無いケースでサロンの手数が増えるため）。
    「推奨バッジは SMSとメール・既定選択は SMS」というズレは意図した仕様。
  - **来店時刻の入力欄は無い**（来店予定日のみ）。そのため手動作成の請求は送信本文の予約日時が**日付のみ**になる
    （「2. 送信」参照）。
- 取り込み: `cancel-billing-service-api/src/services/salonboard-import.service.ts` が「送信前（`pre_send`）」で作成。
  取り込み時点では顧客通知を送らない。
  - 作成時点の **店舗名・住所スナップショット**（`shop_name` / `shop_address`）も取り込んだ店舗の値で保存する
    （手動作成と揃え、送信本文の店舗名解決を両経路で同一にする・GTSS-817 #27）。
- 保存先: **Aurora PostgreSQL `cancellations` テーブル**（drizzle。旧 DynamoDB は移行元のみ・ランタイム不参照）。

### 2. 送信（決済リンク送信）

- 「送信前」の請求は一覧の「送信」ボタンから送信する（運営=管理画面 / サロン本人=ポータル。サロンは自社配下のみ）。
  サービスは `cancellation-send.service.ts`。`status='pre_send'` の条件付き更新で二重送信を防止する。
- 手動作成は作成時に同経路で送信する（`invoice.service.ts` の createInvoice）。
- Stripe Checkout Session を作成し、顧客にメール (SES) / SMS (Twilio) で決済リンクを送信。
  **通知方法（メールのみ／SMSのみ／両方）は請求作成時に `notification_method` として記録し、送信時は
  その記録値を使う**（記録が無い旧データのみ連絡先の有無から導出: 両方→both / メールのみ→email /
  電話のみ→sms）。送信後ステータスは請求中(`pending`)。
- **決済リンクはメール・SMS とも `{API}/pay/{請求ID}` の短縮 URL に統一**（GTSS-886）。生の Stripe
  Checkout URL は作成から最大 24 時間で失効するため本文に直接載せない。/pay が状態・期日ゲートと
  失効時の再発行を担い、支払期日まで支払い可能であることを担保する（下記「決済リンクの有効期限」）。
- **送信時に支払期日（`due_date`）が未設定なら翌月末日（JST）を自動設定する**（GTSS-886。取り込み請求も
  これで必ず期日を持つ）。手動作成は従来どおり作成時に設定（未指定は翌月末日・翌月末日が上限）。
- **初回送信の記録**（GTSS-886 / 法的証跡）: 全送信経路で送信実行時に `first_sent_at`（成否を問わず
  試行時刻）と送信履歴（`cancellation_notifications`。回=1・チャネル・成否・非PIIエラー・SMSセグメント数・
  文面テンプレートver・プロバイダID）を記録する。この値が自動リマインドの起算日になる。
- メール末尾に自動送信の注記（「※ 本メールは{サロン名}からのご案内をシステムにより自動送信しています。」）を
  常に記載する（初回・リマインド共通）。通知方法が「両方」のときは SMS 併記注記も出す（従来どおり）。
- **本文の冒頭に予約日時（来店予定日＋来店時刻）を差し込む**（GTSS-896）。どの予約に対する請求かを本文だけで
  判別できるようにするため、「ご予約に関しまして、当店キャンセルポリシーに基づきキャンセル料が発生しております。」
  の行の先頭へ `{予約日時}の` を前置する（例:「2026年7月7日17時00分のご予約に関しまして、…」）。
  対象は**初回請求メール（HTML／テキスト）・初回請求 SMS・リマインド SMS**（リマインドメールは初回メールと
  同一本文の共用のため自動的に反映される）。
  - **書式は `YYYY年M月D日H時MM分`**。年は 4 桁、月・日・時は先頭ゼロなし、**分は必ず 2 桁**
    （`2026-07-07` + `17:00` → `2026年7月7日17時00分` / `2026-01-05` + `09:05` → `2026年1月5日9時05分`）。
  - **来店時刻が無い／形式外の請求は日付のみ**（`2026年7月7日のご予約に関しまして、…`）。
    **来店予定日が無い／形式外の請求は差し込まない**（助詞「の」も出さず、導入前と完全に同一の本文）。
  - 来店予定日は保存値が JST の暦日（`YYYY-MM-DD`）である前提で**文字列のまま解析**する（日時型へ変換して
    実行環境のタイムゾーンで読み直さない）。来店時刻は `H:MM` / `HH:MM` を受理する（**ゼロ埋め非保証**）。
  - **サロンポータルの請求作成フォームには来店時刻の入力欄が無い**ため、手動作成の請求は**日付のみ**になる。
    実運用で時刻まで出るのはサロンボード取り込みの請求（API を直接叩いて `startTime` を渡した場合も出る）。
  - ⚠️ **決済画面の品目説明欄は対象外**（従来どおり日付のみ）。**領収書には予約日・予約時刻とも出ない**
    （領収書の SUMMARY は事業者名 + T 番号のみ。下記「出力先ごとの対応表」参照）。結果として
    「メール／SMS は分まで・決済画面は日付まで・領収書は出さない」という**書式が併存する**
    （意図的な非対称。実装も別関数のまま）。
  - 実装: `cancel-billing-service-api/src/utils/appointment-datetime.ts`（純関数）＋
    `src/services/notification.service.ts`（4 テンプレートへ前置）。**整形はこの 1 箇所だけが持つ。**
    管理画面の文面再構成は同じ関数の戻り値を API レスポンス（`notificationAppointmentPrefix`）として
    受け取り、`appointmentDate` / `startTime` から再導出しない（`notificationSalonName` と同じ方針。
    フロントに二重実装を置くと書式や形式外値の扱いがドリフトして法的証跡の同一性が崩れるため）。
- **SMS は冒頭の宛名・差出人行・本題を 1 行に連結する**（GTSS-896 追加対応 / 2026-08-14 依頼）。
  端末の SMS 一覧（受信ボックス）は本文の**先頭だけ**をプレビューに出すため、宛名だけの行で始めると
  一覧では「{お客様名}様」しか読めず、どのサロンからの通知か分からない。信頼性を上げるため、
  一覧のプレビューにサロン名まで載るよう先頭ブロックを 1 行にする。

  ```
  {お客様名}様 {店舗名} {担当スタッフ名}です。{予約日時}のご予約に関しまして、当店キャンセルポリシーに基づきキャンセル料が発生しております。

  恐れ入りますが、下記リンクよりお支払いをお願いいたします。

  ▼お支払いはこちら
  https://api.cancel.co.jp/pay/{請求ID}
  ※本SMSは通知専用です。
  ```

  - 対象は **顧客へ送る SMS 3 種すべて**（初回請求 SMS・リマインド SMS・支払い完了 SMS）。
    **メール（HTML／テキスト）は変更しない**（一覧プレビューの制約はメールには無いため）。
  - **段落間の空行は残す**。詰めるのは先頭ブロックだけで、リマインド SMS は本題の直後に空行が
    1 行増えて初回と同じ構成になる。
  - 担当スタッフ名が無ければ「{店舗名}です。」。店舗名が未設定なら事業者名、それも無ければ『サロン』
    （名乗りの解決順は従来どおり）。支払い完了 SMS だけは店舗名・担当者名の両方が無いと
    **名乗りごと省く**（「{お客様名}様 {本題}」になる）。
  - 文面テンプレート版（`NOTIFICATION_TEMPLATE_VERSION`）は **v2 → v3**。管理画面の「送信した文面」
    再構成は v3 で行構成そのものが変わるため、**版別に組み立てを分けている**（`SMS_BODY_BY_VERSION`）。
    リリース前に送った v1 / v2 の記録は従来の 4 行構成のまま再構成される（過去の証跡は変わらない）。
  - **SMS の文字数は増えない**（初回 −2 文字 / リマインド −1 文字。改行 3 個が空白 1 個に置き換わるため）。
- **決済リンク生成時に、連結アカウント上へ「言語＝日本語」の顧客情報（Stripe Customer）を作成して紐づける**
  （GTSS-850 #42）。Stripe の領収書メールを日本語テンプレートで送るための措置で、**顧客メールアドレスの
  登録有無に関わらず必ず作成する**（メールがあれば顧客情報にも設定する）。顧客情報の作成に失敗した場合は
  エラーを記録したうえで従来どおりの決済リンクを生成し、送信は止めない（その決済の領収書は従来の言語になる）。
  適用は決済リンクを作る 2 経路（`invoice.service.ts` / `cancellation-send.service.ts`）＝ 3 API 経路すべて。
  既存の決済リンクには遡及せず、**リリース後に新規発行される分から**日本語になる。技術的な制約（連結アカウント
  上に作る必要／`customer` と `customer_email` の排他）は `docs/tech/stripe-connect.md` を参照。
  - **決済画面のメールアドレス欄は「編集不可」に変わる**（GTSS-850 #42 / AC-4.2 で許容と判断）。顧客情報を
    紐づけると Stripe は登録済みメールをプリフィルし**編集させない**仕様（従来の「メールアドレス直接指定」は
    プリフィルのみで編集可だった）。ただし**領収書の送信先はサロンが登録したアドレスで固定**されており、
    従来も顧客が決済画面でメールを書き換えても領収書の宛先は変わらなかったため、**顧客に届く領収書の宛先は
    変更前と同一**。「書き換えれば宛先が変わる」という誤解を招く表示が解消される側面もあるため許容する。
    → **誤ったアドレスを登録した場合の回復手段はサロン側の修正のみ**（顧客側では訂正できない）。
  - 顧客メールアドレスは**前後の空白を除去した値**で有無を判定し、Stripe へ渡す値（顧客情報・領収書送信先）も
    同じ除去後の値で統一する。空白のみの入力は「未登録」として扱う。
- **送信時の店舗名／住所（SMS／メール本文・Stripe Checkout の品目説明欄）**: 次の順で解決する（GTSS-817 #27）:
  1. `cancellation.shop_name` / `shop_address`（作成時点のスナップショット。**手動・取り込み両経路で保存**）
  2. `shopId` から解決した店舗（スナップショットが空の旧データのフォールバック）
  3. 会社名（`partnerName` / `businessName`。**住所は会社名フォールバックなし**＝住所が無ければ住所は空）
  これにより手動・取り込みの双方で、本文に出るのが会社名ではなく**発生店舗名**になる（取り込み請求も従来の
  会社名表記から発生店舗名へ変わる＝意図的な変更）。
  > この解決順が効くのは **SMS／メール本文と Checkout の品目説明欄**であり、**カード利用明細ではない**
  > （明細は連結アカウント側に `{法人名}キャンセル料`／カナを静的設定済み）。また後述の**領収書 SUMMARY 欄は
  > 店舗名ではなく事業者名**を出す（意図的な出し分け）。

- **領収書 SUMMARY 欄の発行者名（＋適格請求書登録番号）**: 顧客が決済すると Stripe が領収書メールを自動送信する。
  その「SUMMARY」欄（Checkout Session の `payment_intent_data.description`）には、上記の店舗名ではなく
  **事業者名（発行者名）** を出す（GTSS-851 #44）。解決順は次のとおり:
  1. **屋号**（`applications.business_name`）
  2. **法人名／個人事業主名**（`applications.partner_name`）
  3. 固定文字列『サロン』
  > ⚠️ フィールド名と意味が直感と逆（`business_name` = 屋号 / `partner_name` = 法人名）。なお `business_name` は
  > 現行の入力経路が無く旧移行データにしか値が入らないため、**実運用では `partner_name`（法人名）に解決**され、
  > 領収書ヘッダ（連結アカウントの `business_profile.name`）と一致する。
  - サロンが**適格請求書登録番号（T番号）を登録している場合のみ**、発行者名の後ろへ
    `{発行者名}（適格請求書登録番号: {T番号}）` の形で併記する。未登録なら発行者名のみ（括弧も付かない）。
  - T番号を併記する場合に限り、発行者名が 100 文字を超えるなら 100 文字＋`…` に切り詰めてから連結する
    （末尾の登録番号が欠落しないための防御）。未登録時は切り詰めない。
  - **店舗名を SUMMARY に出さない理由**: 適格請求書の発行者名は T番号 の登録事業者を指すべきで、複数店舗を持つ
    サロンで個々の店舗名を出すと登録事業者と一致しなくなるため。
  - 適用範囲は決済リンクを作る**2経路すべて**（ポータルの請求書発行 `invoice.service.ts` / 送信ボタン経由の
    `cancellation-send.service.ts`）。既存の決済リンクには遡及せず、**リリース後に新規作成される分から**有効。
  - ⚠️ **連絡先が電話番号のみの請求（SMS 通知）で領収書メールが届くかは未確定**。当サービスが指定する
    `receipt_email` は顧客メールが登録されている場合のみ設定されるが、Checkout は決済画面で顧客にメール
    入力を求めるため、そのアドレスへ Stripe が領収書を送る可能性がある（GTSS-850 #42 の調査で提起。
    実決済での確認は同 Issue の人力テスト H-1 / H-4 待ち）。届かない場合はこの表示も届かない。
    > 公式ドキュメントで確認できたのは「顧客情報に有効なメールが無い場合、Checkout は決済画面で入力された
    > メールを顧客情報へ設定する」という挙動まで。したがって**言語（日本語化）はこの経路でも効く**が、
    > 「送信先未指定でも領収書が実際に送られるか」は未確認のまま（H-1 / H-4 待ち）。

- **出力先ごとの対応表（混同注意）**:

  | 出力先 | 出る値 | T番号 |
  |---|---|---|
  | 領収書メールの SUMMARY（`payment_intent_data.description`） | **事業者名**（屋号 → 法人名 → 『サロン』） | **併記する**（登録時） |
  | 決済画面の品目説明（`product_data.description`） | 店舗名 / 住所 / 担当者名 / **予約日（日付のみ）** | 併記する（登録時。**領収書には出ない欄**） |
  | 顧客宛メール本文・SMS 本文 | 店舗名（snapshot → shop → 会社名） / **予約日時（分まで。時刻が無ければ日付のみ）** | 出さない |
  | カード利用明細（`statement_descriptor*`） | 連結アカウントに静的設定した `{法人名}キャンセル料` / カナ | 出さない |
  | 領収書メールのヘッダ（発行元） | 連結アカウントの `business_profile.name`（＝ `partner_name`） | 出さない |

  T番号の登録手段（ユーザーポータルのアカウント設定）は `docs/product/application-flow.md`、
  Stripe 側のどのフィールドが領収書に出るかは `docs/tech/stripe-connect.md` を参照。

### 3. 顧客による決済

- Stripe Checkout ページで決済 → リダイレクト先で結果表示（`cancel-billing-service-lp` の PaymentSuccess / PaymentCancel）。

### 4. Webhook 受信

- Stripe Webhook を `cancel-billing-service-api` で受ける（`checkout.session.completed`, `account.updated`）。
- 必須環境変数 `STRIPE_WEBHOOK_SECRET`。受信後にステータスを `paid` へ遷移（二重計上防止のガード付き）。
- 請求の特定はセッション ID（`findByStripeSessionId`）が基本。不一致の場合は **`client_reference_id`
  （請求 ID）でフォールバック突合**する（GTSS-886。/pay の再発行が同時アクセスで競合し、保存されなかった
  側のセッションで決済された場合も着金を取り逃さない）。
- `paid` 遷移できた回だけ、**サロンへ支払い完了メール**・**顧客へ支払い完了 SMS** を送る（重複配信では送らない）。
  支払い完了 SMS も冒頭の宛名・名乗り・御礼を 1 行に連結する（GTSS-896 追加対応。上記「2. 送信」参照）。

  ```
  {お客様名}様 {店舗名} {担当スタッフ名}です。キャンセル料のお支払いありがとうございます。お客様のお支払いを確認いたしました。

  お支払い金額：¥{金額}
  お支払い日：{お支払い日}
  ```

  この SMS は送信履歴（`cancellation_notifications`）へ記録せず、管理画面の文面再構成の対象でもない
  （＝ `NOTIFICATION_TEMPLATE_VERSION` の対象外）。文面は `notification.service.ts` の
  `generatePaymentCompleteSmsContent` が持つ。

### 5. payout

- キャンセル料は **direct charge**（`checkout.sessions.create(params, { stripeAccount })` ＋ `application_fee_amount`）
  で連結アカウント（サロン）上に発生する。GTSS の手数料と Stripe 手数料を引いた net が連結アカウント残高に積まれ、
  月次バッチの `payouts.create` でサロンへ入金される（詳細は `docs/tech/stripe-connect.md`）。

## 自動リマインド送信（7日目・14日目 正午 / GTSS-886）

未払いキャンセル料の回収率を高めるため、**初回送信日を起算日として 7 日目と 14 日目の正午 12:00（JST）**に
同一文面のリマインドを自動送信する（リマインド 2 通・初回含め計 3 通）。バッチ action
`send-billing-reminders`（毎日正午の EventBridge Scheduler。`docs/tech/batch-jobs.md`）が担う。

**法的建付けが仕様の必須要件**（顧問弁護士確認 2026-07）: 未払いへの再通知は非弁行為（弁護士法72条）と
評価されるリスクがあり、「当社の分析・判断が介在しない自動・定型・一律の機械的通知」「回数は初回含め 3 回」
「通知主体はサロン名義」を建付けとする。このため:

- 回数・間隔・時刻・**文面テンプレート**は**全サロン・全請求で共通・変更不可**。サロン・運営いずれにも個別の
  停止・再送・文面変更の操作機能を**設けない**（設計上存在しないこと自体が要件。管理画面・ポータルとも
  再送/停止ボタン無し）
  > **「変更不可」の意味**（GTSS-896 で明確化）: サロン・運営に個別の文面変更手段を設けない、ということ。
  > テンプレート自体は全サロン・全請求で共通のまま、**請求レコードに保存済みの事実値（予約日時）だけが
  > 機械的に差し込まれる**ため、送信される本文は請求ごとに異なる。当社・サロンの分析や判断は介在しない。
  > 画面の注記文言も同趣旨で「文面」→「**文面テンプレート**」に改めている（管理画面 2 箇所・ポータル 1 箇所）。
  > ⚠️ リマインド SMS への予約日時差し込みは**リリース前に法務（顧問弁護士）の確認を取ること**（GTSS-896 / AC-10.1）。
- **夜間ガード**: JST 21:00〜翌 8:00 に起動された場合は送信せず終了する（貸金業法・サービサー法の
  時間帯規制に準拠。スケジューラ再試行遅延の安全弁）
- 回を追って文面を強めない（リマインド 2 通は同一文面）。禁止文言（至急/法的措置/督促/催告/回収/訴訟/弁護士 等）を
  含めない（unit テストで固定）

**対象条件**（実行時点で判定）: ステータスが「請求中」・`first_sent_at` 記録あり（＝リリース後に送信された
請求。リリース前は恒久的に対象外）・支払期日を過ぎていない（**期日当日は対象**・期日超過後は送らない）。
手動作成・サロンボード取り込みの両経路に一律適用。サロン側の設定・操作は一切ない。

**回の判定**（JST 暦日の経過日数）: 経過 7 日以上 14 日未満で 2 通目未試行 → 2 通目。経過 14 日以上で
3 通目未試行 → 3 通目（2 通目未試行でも 3 通目のみ送る＝**欠番。後追い送信しない**）。1 回の実行で同一請求に
送るのは最大 1 通。バッチ障害等で当日送れなかった場合は翌日以降の正午に同条件で送られる（キャッチアップ）。

**二重送信防止**: `cancellation_notifications` の UNIQUE `(cancellation_id, round, channel)` ＋ 回単位の
claim（`processing` で先行 insert → 配信 → success/failed へ確定。`payout_runs` の claim パターン踏襲）。
**回の送信済み判定は回単位**: 当該回の記録が 1 チャネル分でも存在すればその回は試行済み（残チャネルの
後追い・失敗チャネルの再送はしない。claim 後クラッシュの `processing` 残留も試行済み扱い）。

**失敗分離**: 1 件・1 チャネルの送信失敗は他チャネル・他請求・次回リマインドに影響しない（自動再送なし・
失敗も履歴に記録）。初回が全チャネル失敗した請求でもリマインドは予定どおり送る（機械的一律）。
**送信失敗のアラート・失敗一覧・失敗絞り込みは設けない**（再送手段が無く対応が取れないため。
記録は管理画面の請求詳細の送信履歴から参照する）。

**文面**: 通知方法は初回請求の記録値を踏襲。リマインドメールは**初回と同一本文**（差し替えは SMS のみ）。
リマインド SMS は初回のお願い文を「お支払いが確認できておりませんため、再度ご案内いたします。お支払い済みの
場合はご容赦ください。」へ差し替えた確定文面（宛名は「{お客様名}様」スペースなし）。決済リンクは初回と同一の
/pay 短縮 URL。**リマインド SMS の冒頭にも初回と同じ予約日時が入る**（GTSS-896。上記「2. 送信」参照）。
**リマインド SMS も初回と同じく冒頭の宛名・差出人行・本題を 1 行に連結する**（GTSS-896 追加対応。
上記「2. 送信」参照）。差し替え文の前に空行が 1 行入り、初回 SMS と同じ段落構成になる。

**SMS 長**: **想定条件（店舗名 40 字／担当 10 字／顧客 10 字）で 335 文字（5 セグメント）以内**であることを
自動テストで検証する（GTSS-896 で 268 文字／4 セグメントから改定）。**サーバー側の文字数制限・切り詰めは
無く**、入力欄は店舗名・担当者名・顧客名とも各 100 字まで許容するため、**これはハード上限ではない**
（テストが置いている現実的な上限）。
予約日時の差し込みで本文は 15〜18 文字増える。通常の UI 運用で来店時刻を持つのはサロンボード取り込みの
請求だけ（API を直接叩けば手動作成でも `startTime` を設定できる）で、
その請求 ID は `imp_` + UUID の **40 文字**（手動作成の `inv_` + エポックms は 17 文字）——
**本文が長くなる側だけ ID も 23 文字長い**ため、想定最大（店舗名 40 字／担当 10 字／顧客 10 字）の
リマインド SMS は **269 文字＝5 セグメント**になり旧上限を満たせない（dev は API ドメインが 4 文字長く 273 文字）。
（冒頭 1 行化前は 270 / 274 文字。GTSS-896 追加対応で改行 3 個が空白 1 個に置き換わり 1 文字短くなった。
セグメント数は変わらない。）
文面は法務確認済みで短縮できないため上限側を実態に合わせた。**取り込み請求では標準的な店舗名でも初回 SMS が
3 → 4 セグメントに増える**ため、Twilio の送信コスト増を前提として見込むこと。決済リンクの短縮
（請求 ID の短縮・短縮 URL の導入）は今後の課題。

**モニタリング**: 実行ごとに対象件数・回別（7日目/14日目）・チャネル別の送信数と成否を構造化ログ
（`[billing-reminders] summary:`）へ集計出力。支払い率等は送信履歴 × `paid_at` の SQL 集計で算出可能
（専用計測基盤は新設しない）。SMS セグメント数も履歴に記録しコスト増加幅の把握に使う。

## 決済リンクの有効期限（支払期日）と /pay ゲート・再発行（GTSS-886）

支払期日（`due_date`）を**決済リンクの有効期限**とする。期日まではリンクから支払可能・期日超過後は支払不可。

- **リンクの一本化**: 顧客に送るリンクは初回・リマインドとも同一の `{API}/pay/{請求ID}`（メールも SMS と
  同じ短縮 URL 方式へ統一）。
- **/pay のゲート**: アクセス時に「請求中」かつ期日内（期日当日 23:59:59 JST まで）であれば決済ページへ 302。
  支払期日超過／支払済／取消済／失敗はシンプル HTML の案内（「お支払い期限が過ぎているか、既にお手続き済みの
  ためお支払いいただけません」）を表示。リンク未発行は従来どおり 404 の案内。**リリース前の既存請求にも適用**
  （期日未設定の既存請求は期日チェックのみスキップし、状態ゲート・失効時再発行は適用）。
- **失効時の再発行**: Stripe Checkout Session は作成から最大 24 時間で失効する（従来は実質 24 時間しか
  支払えていなかった既知不具合を本ゲート＋再発行が解消）。保存済みセッションが失効している場合のみ、
  **初回送信時と同一のセッション生成ロジック（共通ビルダー `checkout-session.service.ts`）**で再発行して誘導する
  （手数料・領収書SUMMARY/T番号・日本語Customer・領収書送信先・店舗名解決を含む全パラメータが初回と同一）。
  保存は条件付き更新（先勝ち）。セッションの失効時刻は「作成から 24 時間」と「支払期日 23:59:59 JST」の
  早い方（Stripe の最小 30 分制約により期日末尾 30 分以内は最大 30 分の食み出しを許容）。
- **client_reference_id**: 全セッションに請求 ID を設定し、webhook のセッション ID 突合が外れた場合の
  フォールバック突合に使う（再発行競合時の着金取り逃し防止）。
- **取消時のセッション失効**: 請求が取消済へ変更された時点で有効なセッションが残っていれば失効させる
  （ベストエフォート。失効失敗で取消操作は失敗させない）。取消前に開かれた決済画面からの駆け込み決済が
  着金した場合は現行どおり支払済へ遷移し、返金は運用対応。

## 期限切れ（未回収）と配信進捗（派生情報 / GTSS-886）

既存ステータス（SSOT）は**変更しない**。以下 2 つを派生情報として API レスポンスに追加フィールドで付与する:

- **期限切れ（未回収）**: 「請求中」かつ支払期日超過（JST 暦日で期日 < 今日）の請求。`isExpired`（boolean）で
  返し、フロント・CSV は**表示ラベルのみ**「請求中」→「期限切れ（未回収）」（バッジは「期限切れ」グレー系）に
  置換する（`status`/`statusLabel` は `pending`/`請求中` のまま）。期日未設定は期限切れ判定しない。
  リリース前の既存請求にも適用。期限切れ表示中に決済完了すれば通常どおり支払済になる。
  管理画面・ポータルのサマリーカード「請求中」は期限切れ分を**除外**（排他）し、「期限切れ（未回収）」カードを
  別に持つ。ステータスフィルタにも「期限切れ（未回収）」を追加（「請求中」は期限切れを含まない）。
- **配信進捗**: 送信履歴の最大試行回から導出（1 回目のみ=「初回請求」／2 回目まで=「2回目」／3 回目まで=
  「3回目」。**成否を問わず試行した回をカウント**）。履歴の無い請求（リリース前送信分・送信前）は「-」表示。
- **API レスポンス**: 一覧・詳細の各行に `firstSentAt` / `deliveryRound` / `deliveryProgressLabel` /
  `lastReminderSentAt` / `isExpired` を追加。**送信履歴の明細（`notifications[]`: チャネル別成否・エラー種別・
  セグメント数）は admin 経路（`GET /cancellations`・`GET /cancellations/:id`）にのみ含め、サロン向け
  （`GET /invoices` 等）には返さない**（露出最小化。エラー詳細もサロンへ返さない）。
- **管理画面の請求詳細**: 送信履歴タイムライン（回別の送信日時・自動送信ラベル・チャネル別成否・未送信予定回・
  リンク失効予定）、記録されたテンプレートバージョンからの文面再構成表示、法的建付けの注記ボックスを表示。
  再送・停止のボタンは存在しない。フロントは API の派生値を使い再計算しない（JST 判定の不一致防止）。

### 文面テンプレートのバージョン（法的証跡 / GTSS-896）

送信履歴（`cancellation_notifications.template_version`）には**送信時点の文面テンプレート版**を記録し、
管理画面はその版から**送信済み文面を再構成して表示する**（本文そのものは保存しない）。

| 版 | 文面 | 記録される期間 |
|---|---|---|
| `v1` | 予約日時なし（GTSS-886 の文面） | GTSS-896 リリース前に送信した分 |
| `v2` | 冒頭に予約日時を差し込んだ文面（GTSS-896） | （v3 を同時リリースするため実データ上は発生しない見込み） |
| `v3` | SMS の冒頭 3 行（宛名 / 空行 / 差出人行）と本題を 1 行に連結した文面（GTSS-896 追加対応）。メール本文は v2 と同一 | GTSS-896 リリース後に送信する分 |

- **再構成は通知レコード単位で版を見る**（請求単位で決め打ちしない）。リリース前に初回を送った請求が
  リリース後に 2・3 通目のリマインドを受けるため、**同一請求で v1 と v3 が混在する**。
- **v3 は「予約日時の有無」ではなく行構成そのものが変わる**ため、管理画面の再構成は接頭辞の差し替え
  （`APPOINTMENT_SENTENCE_BY_VERSION`）だけでなく**組み立て自体を版で分けている**（`SMS_BODY_BY_VERSION`）。
  版を足すと網羅マップがコンパイルエラーになり、明示的に組み立てを書くまで通らない。
- **過去版の再構成ロジックは削除しない**（既に送った請求の証跡が変わってはならない）。
  **未知の版は再構成しない**（誤った文面を証跡として見せない）。
- ⚠️ **リリース順序**: API のテンプレート版を上げる前に**管理画面（新版の再構成）を先にリリース**すること。
  逆順にすると、API リリース直後に送信した `v3` の履歴を管理画面が再構成できず「送信した文面」が
  表示されない期間が生まれる。切り戻しは逆順（API → 管理画面）。
- **本文は請求ごとに変わる**（予約日時が入るため）。同一性の担保は「全請求で同一の本文」ではなく
  「**全請求で同一のテンプレート＋請求レコードの事実値**」で成り立つ。送信履歴に本文を保存しない方針
  （記録するのはテンプレート版のみ）は維持する。
- 送信後に来店予定日・来店時刻を書き換える経路は現状無いため再構成のズレは生じない。将来これらを
  編集可能にする場合は証跡の同一性が崩れる点に注意すること。
- **再送で配信できたら履歴の版は最新化される。** 決済失敗（`failed`）→ 運営が「送信前」へ巻き戻す →
  再送、という経路はリリースを跨いで成立し得る。この場合**顧客に届くのは新しい版の本文**なので、
  **配信できた（`success`）試行の版だけ**を `template_version` へ書く（`status` / `sentAt` は先勝ちのまま
  ＝初回試行の実績）。**失敗した再送では版を書き換えない**（届いていない文面を「送信した文面」として
  見せないため）。結果として `template_version` の意味は「**最後に配信できた文面の版**（一度も配信
  できていなければ最初の試行の版）」になる。
  なお 2 回目以降の**配信成否**が履歴に残らない点は GTSS-886 からの既知の非対称で、解消には
  送信履歴へ試行連番を持たせるスキーマ変更が要る。
- ⚠️ **予約日時の書式を変える新版を作る場合は、接頭辞の返し方も版別にすること。**
  管理画面へ返す `notificationAppointmentPrefix` は**現行テンプレートの書式で解決した 1 値**なので、
  同一請求内で版が混在し、かつ**版ごとに書式が違う**場合は表現できない（今の v1/v2 は「差し込む／
  差し込まない」の違いだけなので 1 値で足りる）。書式自体を変える版を足すときは、版別の接頭辞解決か
  送信時スナップショットの保存へ切り替える。

## 精算用CSVの出力（代理店コード・支払日列／支払日期間フィルタ）

運営が月次精算の元データとして、キャンセル請求管理画面（admin）から**CSVを出力**できる（GTSS-836 / #30）。
CSVはクライアント側で生成し、画面の絞り込み結果（`filteredInvoices`）をそのまま書き出す。詳細は
`docs/product/agent-code.md`。

- **追加2列（GTSS-836・末尾）**: 既存16列の末尾に **代理店コード**（発生元申込の `agentCode`。未設定は空）と
  **支払日**（支払い完了日時 `paidAt` を JST 表示。未払い行は空）を追加する。既存列順・PII列（お客様名/
  電話/メール）は不変。**CSVに口座番号は出力しない**（元々データに存在しない）。5%額・料率・
  還元期間などの計算は含めない（生データのみ）。
- **追加4列（GTSS-886・末尾）**: 18列の末尾にさらに **配信進捗**（初回請求／2回目／3回目。履歴なしは空）・
  **初回送信日**（`firstSentAt` の JST 日付。記録なしは空）・**支払期日**（`dueDate`）・
  **リマインド送信日**（最新リマインド送信日時の JST 日付。未送信は空）を追加し **22 列**とする
  （既存列の並び・名称は不変＝経理の取り込みを壊さない末尾追加方式）。
  **注意**: 既存「ステータス」列に新しい表示値「期限切れ（未回収）」が出現する（`isExpired` の行のみ。
  列構成は不変だが値が増える。経理の実取込での受入確認はリリース前の人力テスト H-6）。
- **支払日期間フィルタ**: 絞り込みバーに支払日の開始日・終了日の日付ピッカーを追加。指定すると、支払日が
  その範囲（JST 暦日・両端含む）に含まれる請求のみが**一覧表示・CSV出力の対象**になる。範囲外および**未払い
  （支払日なし）請求は除外**。未指定のときは全件（支払日の有無に関わらず）が対象。期間指定は一覧と CSV の
  双方に効く（`filteredInvoices` が CSV 出力元のため）。
- **元データ（API）**: `GET /cancellations`（**管理者専用 = `requireAdmin`**）の各行に発生元申込の
  `agentCode` を付与する（会社スコープ `?applicationId=`・グローバル一覧の双方で同一形状）。支払日 `paidAt` は
  既にレスポンスに含まれる。CSVおよびこの元データは admin 限定であり、代理店へ共有する非PIIデータは運営が
  スプレッドシートへ手転記して生成する（顧客PIIを代理店へ渡さない）。

> 実装: `cancel-billing-service-admin/src/constants/cancellationStatus.ts`（CSVヘッダ/行・`filterCancellations`
> の `paidFrom`/`paidTo`）/ `src/components/CancellationManagement.tsx`（支払日ピッカー）/
> `cancel-billing-service-api/src/repositories/cancellations.repository.ts`（一覧へ `agentCode` 付与）。

## データモデル（Aurora PostgreSQL）

`cancellations`（`cancel-billing-service-api/src/db/schema.ts`）。主なカラム:
- `id` (PK, UUID) / `applicationId` (FK→applications) / `status`（上表 SSOT）
- `customerName` / `customerNameKana` / `customerEmail` / `customerPhone`（顧客 PII。退会時マスク）
- `amount`（キャンセル料）/ `appointmentAmount`（予約金額）/ `paidAmount` / `platformFee` / `stripeFee`
- `appointmentDate` / `startTime` / `menuName` / `staffName`
- 発生店舗: `shopId`(FK→`shops.id`、当サービスの店舗マスタ) / `shopName` / `shopAddress`
  - **表示**（一覧・詳細）は `shopId` から解決した店舗マスタ名・住所（`storeName` / `storeAddress`）を使う。
    店舗は**論理削除のみ**（`deletedAt`）で物理削除しないため `shopId` は保持され、削除後も JOIN で解決できる
    （DB の FK は安全弁として `ON DELETE SET NULL` だが通常フローでは発火しない・GTSS-817 #27）。
  - `shopName` / `shopAddress`（`cancellations` 列）は**送信本文の凍結用スナップショット**で、手動・取り込み
    両経路で作成時点の値を保存する。詳細表示には使わない（`storeName`/`storeAddress` と二重表示しない）。
- 取り込み（GTSS-817）: `source` / `externalReservationId` /
  `reservationStatus` / `cancellationType` / `paymentType` / `cancellationPolicy` / `receivedAt`
- 冪等キー: `(shopId, externalReservationId)` 部分ユニーク（手動作成は `externalReservationId` NULL で対象外）
- リマインド（GTSS-886）: `firstSentAt`（初回送信試行日時。NULL=リリース前送信分=リマインド対象外）。
  抽出用部分インデックス `cancellations_reminder_target_idx`（status='pending' かつ first_sent_at あり）

`cancellation_notifications`（送信履歴・GTSS-886）:
- `id` / `cancellationId`(FK→cancellations, CASCADE) / `round`(1=初回, 2=7日目, 3=14日目) /
  `channel`('email'|'sms') / `status`('processing'=claim直後|'success'|'failed') / `errorCode`・`errorDetail`
  （非PII。コード/種別のみ）/ `smsSegments` / `templateVersion` / `providerMessageId`（SES MessageId /
  Twilio SID）/ `sentAt` / `createdAt`
- UNIQUE `(cancellation_id, round, channel)` — 二重送信防止の土台（回単位 claim 先行 insert）
- **PII 方針**: 宛先（メール・電話）と送信本文は保存しない。画面の文面表示は `templateVersion` からの
  再構成で行う（**テンプレートが全請求共通**で、差し込まれるのは請求レコードに保存済みの値だけのため
  同一性が担保される。予約日時により**本文自体は請求ごとに変わる** → 上記「文面テンプレートのバージョン」）。
  エラー詳細は保存前に PII を除去
